## 1. 프로젝트 캔버스

| 항목 | 작성 내용 |
|---|---|
| 해결하려는 문제 | 각 부서는 예산서와 근거 자료를 검토 부서(경영기획, 재무)에 내는데, 검토자가 무엇을 물을지 미리 알지 못해 근거 부족과 질문을 받은 뒤에야 보완하고 여러 번 다시 제출한다. 검토의 본질은 "주장마다 받쳐 줄 숫자가 있는지" 확인하는 일인데, 근거가 되는 실적과 투자 자료는 DART 사업보고서, IR 발표자료, 실적 엑셀, 애널리스트 리포트에 형식과 단위가 제각각인 채로 흩어져 있다. 같은 항목을 회사마다 다르게 부르고(핸드폰, 핸드셋, 단말기) 같은 회사도 해마다 표 구조가 바뀌어, 기존 파서는 회사·연도별로 하드코딩되어 있다. 실제 예산서와 검토 의견은 사내 기밀이라, 구조가 닮은 공개 데이터(사업보고서의 투자 계획 절, 애널리스트 리포트의 쟁점)로 먼저 만들고 검증해야 한다. |
| 대상 사용자 | **주 사용자: 예산서를 작성하는 부서 구성원.** 제출하기 전에 예산서와 근거 자료를 올려, 검토자의 눈으로 근거가 부족한 곳과 예상 질문을 미리 받아 보완한다.<br>그 밖의 이해관계자: 검토 부서(경영기획, 재무 FP&A)는 제출된 예산서를 심의하고, 의사결정자(경영진, 예산심의위원회)는 우선순위를 조정해 승인한다.<br>**서비스 역할:** 분석 담당자(자료를 올리고 결과를 확인), 설정 관리자(부서·검토 기준·프롬프트·AI 모델을 고름), 평가 담당자(예상 질문을 이후 리포트 쟁점과 견주고 판정을 확정)는 사람을 나눈 것이 아니라 서비스 안의 역할이다. 권한을 나누지 않아 모든 사용자가 세 역할을 모두 쓸 수 있다. |
| 프로젝트 목표 | 통신 3사(SKT, KT, LG U+)의 공개 자료를 하나의 파이프라인으로 파싱해 적재하고, 이를 근거로 예산서의 약한 곳을 짚고 검토자(애널리스트 관점)가 던질 질문을 예측하는 **분석 Agent**를 데모 수준으로 구현한다. 예측은 기준 시점 이전 자료로만 수행하고, 이후 발행된 애널리스트 리포트의 쟁점과 견줘 적중률을 정량으로 제시한다. 검토 기준은 애널리스트 관점에 부서별 집중 포인트를 더하는 방식으로 설정에 분리해, 과제 이후 공개 데이터 자리에 사내 예산서와 검토 의견을 연결해 쓸 수 있게 한다. 적재한 재무 데이터는 **인사이트 Agent**(대시보드 + 질의응답)로 직접 보고 물을 수 있게 한다(추가). 2차 현업 멘토링(11.11) 우선순위에 따라 데이터 적재의 정확성을 가장 먼저 확보한다. |
| 제안 솔루션 | 공시와 IR 자료를 같은 파싱 파이프라인으로 정제해, 숫자는 표준 항목 매핑표에 따라 DuckDB에, 본문은 ChromaDB에 발행일과 출처를 달아 적재한다. 정형 데이터(DART API)는 코드와 규칙으로, 반정형(PDF·Excel 표)은 코드로 먼저 추출하고 해석이 어려운 경우만 LLM이 보조하며, 비정형(설명 문장)은 LLM으로 추출한다. 공시에 없는 값은 추정하지 않고 결측으로 남긴다.<br>**분석 Agent:** 사용자가 회사·부서·분기를 고르고 예산서 1개와 근거 자료를 첨부하면, 첨부 순간 회사·기준 시점·형식을 점검해 경고한다. 분석은 주장 추출 → MCP 도구로 근거 검색·재무 조회 → CapEx·감가상각 등은 코드로 계산해 공시와 대조 → 판정(근거 충분/부족)과 예상 질문 생성 순으로 진행한다. 결과는 예산서 원문 위 하이라이트(빨강 점선 근거 부족, 노랑 점선 질문)와 오른쪽 `분석 / 질문` 패널, 분석 보고서·예상 질문 보고서(Markdown/PDF 내보내기)로 보여 준다. `평가하기`는 기준 시점 이후 리포트 쟁점(정답 표)과 예측을 비교해 AI가 1차 판정하고 사람이 확정한다.<br>**인사이트 Agent(추가):** 회사의 DART 적재 데이터를 대시보드(한눈에, 손익, 재무상태, 현금흐름, 설비투자, 동종사 비교)로 보여 주고, 질문하면 답에 쓴 숫자를 출처 표·차트와 함께 답한다.<br>질문 예측 모델은 기준 시점 이전 리포트의 질문과 쟁점으로 파인튜닝해 기본 모델과 비교한다(should). 서비스는 Vue 프론트엔드, Spring Boot 백엔드(채팅은 Spring AI), Python FastAPI AI 서비스, 읽기 전용 MCP 조회 서버로 구성한다. |
| 최소기능(MVP) | • `must` 근거 데이터 수집과 적재: 통신 3사의 IR 자료, 사업보고서, 재무 데이터, 애널리스트 리포트 메타가 발행일과 출처를 달고 쌓인다(화면 없는 파이프라인).<br>• `must` 자료 파싱과 근거 점검: 예산서에서 주장과 숫자를 뽑아 근거가 모자란 곳을 원문 위에 표시하고, CapEx 등은 코드로 계산해 공시와 대조한다. 회사가 다르거나 기준 시점 이후이거나 형식이 맞지 않는 자료는 첨부할 때 경고한다.<br>• `must` 애널리스트 질문 예측: 예상 질문, 왜 묻는지, 준비할 근거를 원문 위치와 함께 정리하고 보고서로 낸다.<br>• `must` 예측 평가: 기준 시점 이전 자료로만 예측하고, 이후 리포트의 쟁점과 견줘 맞힘·부분·빗나감·놓침과 정밀도·재현율을 산출한다.<br>• `should` 범용 설정 6항목: 입력 자료 종류, 추출 항목, 출력 양식, 검토 기준(부서), 프롬프트, AI 모델을 코드 수정 없이 바꾼다. 구현되는 데까지 한다.<br>• `추가` AI 챗봇, 인사이트 Agent, 로그인 화면 |
| 포함 범위 | • 대상: 국내 통신 3사(SKT, KT, LG U+). 데모는 SKT 2025 4Q, 부서 네트워크/인프라, 기준 시점 2026-03-17<br>• 데이터: OpenDART 공시(재무제표, 주석), 각 사 IR 발표자료와 실적 엑셀, 주관 팀 제공 애널리스트 리포트(쟁점과 출처 링크만 저장)<br>• 입력 자료: 예산서 1개(PDF, HTML) + 근거 자료 여러 개(PDF, HTML, XLSX, CSV). 데모 예산서는 SKT 2025 사업보고서 II-3 설비투자 절<br>• 검토 기준: 애널리스트 관점 고정 + 공통 점검 항목 7개 + 부서 8개의 집중 포인트(데모는 네트워크/인프라)<br>• 원본 보관: 파서 테스트와 데이터 복구를 위한 수집 원본 저장<br>• 화면: v03 화면 목록(3-1). 분석 Agent B10~B61, 인사이트 Agent I10~I20, 로그인 S00<br>• 산출물 내보내기: 분석 보고서·예상 질문 보고서를 항목 선택 후 Markdown/PDF로<br>• 검증: 리포트 기반 정답 표 구축과 예측 평가(AI 1차 판정 + 사람 확정)<br>• 모델: 기준 시점 이전 리포트 질문·쟁점으로 만든 학습 데이터로 LLM 파인튜닝(should) |
| 제외 범위 | • 예산서 등 사내 데이터 연결 (과제 종료 후 주관 팀 수행)<br>• 온프레미스 및 로컬 LLM 서버 구축 (AI 모델 토글은 엔드포인트 설정 연결까지만, 확인 필요)<br>• 인증·권한 분리 (로그인은 화면과 역할 태그만)<br>• 뉴스 본문 수집과 활용, 유료 리포트 사용<br>• 손글씨, 스캔본 OCR<br>• 추세나 맥락을 이용한 값 추정 (공시에 없는 값은 결측)<br>• 투자 판단이나 매매 추천<br>• 신규 공시 알림, 강화학습 기반 접근 (MVP 이후 검토) |
| 성공기준 | • 데모 시나리오 완주: ① SKT 2025 4Q 예산서 검토(첨부·경고 → 하이라이트 → 질문 → 보고서 내보내기) ② 평가(이후 리포트와 비교) ③ 부서 토글을 바꿔 다시 분석하면 점검 포인트와 예상 질문이 달라짐 ④ 인사이트에서 CapEx 질문(추가)까지 한 흐름으로 동작한다.<br>• 데이터 정합성(안): 정답 표 대비 숫자 추출 정확도 95% 이상, 표준 항목 매핑 정확도 90% 이상<br>• 예측 성능: 이후 리포트 쟁점 대비 정밀도·재현율을 산출하고, 기본 프롬프트·파인튜닝 전 모델 대비 개선 폭을 제시한다(목표값은 정답 표 구축 후 확정).<br>• 근거성: 출처 없는 숫자 0건, 모든 예상 질문에 원문 위치 연결<br>• 적재 품질 증명(안): 세부 계정 데이터가 있어야 답할 수 있는 예상 질문 시나리오 2~3개 시연 |
| 제약조건 | • 기간: 2026.10.30 ~ 12.16, 약 7주 (11.20 중간점검, 12.16 예선)<br>• 예산: API Key 팀당 $350 / 1개월. 호출량, 임베딩 재생성, 파인튜닝 횟수 관리<br>• 데이터: 공개 자료와 주관 팀 제공 자료만 사용, 리포트는 쟁점과 출처 링크만 저장<br>• 평가: 예측과 파인튜닝 시 기준 시점 이후 자료를 볼 수 없도록 시점별 분리. 이후 자료는 평가 단계에서만 사용<br>• 기술: 공시 숫자, 계산값, AI 해석을 구분 표시하고 숫자마다 기준 시점을 표기. 인사이트 화면은 "연결/별도" 대신 `SKB 포함` / `SKT 단독` / `SKT+SKB 합산`으로 표기<br>• 팀: 6명, 현업 멘토링 격주 |

## 2. 프로젝트 운영 방식

| 항목 | 작성 내용 |
|---|---|
| 선택 방법론 | □ Agile □ MSA □ Scrumban ■ **Hybrid** □ 기타 |
| 선택 근거 | 정의서, 설계서, 11.20 중간점검, 12.16 예선처럼 산출물 제출일이 고정되어 있어 마일스톤은 계획 중심(Waterfall)으로 관리한다. 반면 문서 파싱, 표준 항목 매핑, 예상 질문의 품질은 실험 결과와 격주 현업 멘토링 피드백에 따라 계속 바뀌므로, 구현은 1주 단위 Sprint로 반복 개선한다. 초기에는 전원이 데이터 파싱을 함께 진행하고 이후 데이터, AI, BE, FE, Infra 트랙이 병렬로 움직이기 때문에, 공유 보드로 진행 상황을 함께 본다. |
| 계획·점검 주기 | • 1주 Sprint: 매주 월요일 10시 Sprint 계획(목표와 작업 확정), 금요일 17시 리뷰와 KPT(Keep, Problem, Try) 회고<br>• 데일리 스탠드업: 평일 9시 30분, 15분 이내 오프라인 진행(어제 한 일, 오늘 할 일, 막힌 일), 불참 시 Slack에 미리 공유<br>• 현업 멘토링: 격주, 질문은 팀 내부에서 취합해 진행 상황과 함께 전달하고 결과는 다음 Sprint 계획에 반영<br>• 품질 점검: Sprint 리뷰마다 정답 표 기준 정확도와 정밀도·재현율을 다시 재고 추이 기록 |
| 작업관리 도구 | • Notion: 회의록, 팀 문서, 산출물 관리, WBS, 요구사항 추적표, 테스트 케이스, 결함 관리 데이터베이스<br>• GitHub: 코드 저장소와 멘토 코드 공유, Issues와 Projects로 작업 상태 관리(To Do, In Progress, In Review, Done), Git Flow 브랜치 전략, PR 리뷰(AI 리뷰 봇, 1인 승인)<br>• Slack: 공식 소통 채널, 공지와 중요 결정 공유, 평일 1시간 이내 응답<br>• Google Drive: 산출물 파일 보관과 제출, 주관 팀 제공 데이터 수령<br>• Figma: 화면 설계와 시안 공유<br>• Jenkins, Docker Compose: 빌드와 배포 자동화<br>• Final Project 앱 게시판, 메일: 멘토 질문과 개별 자료 검토 요청 |
| 의사결정 방식 | 팀 합의를 우선하되, 파트 안의 기술 결정은 메인 담당(데이터 성민기, BE 윤혜정, AI 안중범, 임진섭, Infra 주윤겸)의 의견을 우선한다. 의견이 다르면 각자 의견과 근거를 공유하고 장단점을 비교한 뒤 투표로 정하며, 그래도 정하기 어려우면 PM(김준영)이 선택지별 근거와 영향을 정리해 최종 결정한다. 과제 범위나 요구사항을 바꾸는 결정은 팀 회의에서 정하고, 주관 팀의 의도와 관련된 사항은 현업 멘토의 확인을 거친다. 한 번 결정한 사항은 이견이 있어도 모두 존중하고 따른다. |
| 변경 기록 방식 | 결정과 변경 사유는 Notion 회의록의 결정 사항에 날짜, 결정한 사람과 함께 기록하고, 회의록은 PM이 당일 작성해 Slack 팀 채널에 공유한다. 요구사항이 바뀌면 요구사항 추적표에 변경 이력을 남기고 관련 WBS 작업과 연결하며, 코드 변경은 GitHub 이슈와 PR에 요구사항 ID를 달아 남기고, 커밋 메시지는 "타입: 작업내용 #이슈번호" 규칙을 따른다. 프롬프트와 검토 기준처럼 설정으로 분리한 항목은 버전을 붙여 저장해, 버전별 평가 결과를 비교할 수 있게 한다. |
