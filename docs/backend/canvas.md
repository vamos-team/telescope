# 협업 캔버스 설계와 결정 기록

> 작성자 : 윤혜정 (이슈 #82)

> 캔버스 도메인(`backend/.../canvas`)을 어떻게 저장하고, 여러 사람이 동시에 고칠 때 무엇을 지키는지와
> 그렇게 정한 이유를 남긴다. API 경로·필드는 `docs/frontend/api-spec.md` 3장, 공통 규약(권한, 저장 규칙,
> 실시간 연결)은 `docs/backend/api-spec.md` 4·5장, 실시간 전달 방식 선정은 같은 문서 11장을 따른다.

## 1. 범위

| 다룸 (#82) | 다루지 않음 |
|---|---|
| 캔버스 목록·생성·이름 변경·삭제·열기 | 실시간 전달(WebSocket, #83). 이 문서는 커밋 후 알림을 발행하는 지점까지 |
| 공유 명단(소유자·편집·보기) | 화면 연동(#84) |
| 카드·연결 이벤트 저장, 글 충돌, 재전송 중복 방지 | 카드 태그·비교·컨텍스트 계산(ai), 공시·문서 조회(mcp-server) |
| 활동 로그 | 초안·질문·평가 결과물 |
| 권한 확인(HTTP. 실시간 구독도 같은 서비스를 쓴다) | 인증 구현(#34) |

## 2. 테이블 (`app` 스키마, `V9__create_canvas.sql`)

| 테이블 | 주요 컬럼 | 설명 |
|---|---|---|
| `canvas` | `id`, `name`, `quarter`, `owner_id`, `last_seq`, `last_edited_by`, `last_edited_at`, `deleted_at` | 소유자는 여기에만 둔다. `last_seq`는 마지막 이벤트 번호 |
| `canvas_share` | `canvas_id`, `user_id`, `role`(`EDIT`/`VIEW`) | (캔버스, 사용자) 고유. 소유자는 넣지 않는다 |
| `canvas_card` | `id`(UUID), `canvas_id`, `kind`, `x`, `y`, `props`(JSONB), `text`·`text_version`, `prompt`·`prompt_version`, `created_by` | 위치·글을 다른 컬럼에 둔다. 종류별 필드는 `props` |
| `canvas_link` | `id`(UUID), `canvas_id`, `source_card_id`, `target_card_id`, `rel`, `prompt`·`prompt_version`, `created_by` | 양 끝 카드가 지워지면 DB가 같이 지운다(`ON DELETE CASCADE`) |
| `canvas_mapping` | `canvas_id`, `concept_id`, `company`, `cells`(JSONB), `accepted`, `decided_by` | 계정 대응 확정. (캔버스, 개념, 회사)마다 마지막 결정 하나 |
| `canvas_event` | `canvas_id`, `seq`, `request_id`, `author_id`, `type`, `payload`(JSONB) | (캔버스, `seq`) 고유. 고치지 않고 쌓는다 |
| `canvas_request` | `canvas_id`, `request_id`, `author_id`, `first_seq`, `last_seq`, `response`(JSONB) | (캔버스, `request_id`) 고유. 재전송에 처음 응답을 돌려준다 |

카드 종류와 `props`:

| `kind` | `props` | 글 컬럼 |
|---|---|---|
| `table` | `tableId`, `rows`, `cols`, `vcol`, `edits`(`"r,c": 값`), `sort` | `prompt` |
| `compare` | `sources`(원본 표 카드 ID) | `prompt` |
| `doc` | `docId` | `prompt` |
| `dash` | `panel` | `prompt` |
| `chart` | `compareId` | `prompt` |
| `prompt` | — | `text` (프롬프트 카드 본문) |

## 3. 이벤트 묶음 처리 순서 (`CanvasEventService.apply`)

1. 캔버스 행을 잠그고 읽는다(`SELECT … FOR UPDATE`). 없거나 삭제됐으면 404.
2. 편집 권한(소유자·편집)을 확인한다. 아니면 403(`K001`/`K002`).
3. 같은 `requestId`를 이미 처리했으면 저장해 둔 응답을 그대로 돌려주고 끝낸다.
4. 같은 카드의 이동은 묶음 안에서 마지막 위치만 남긴다.
5. 이벤트를 순서대로 적용한다.
   - 형식 오류 → 400 `C001`(`events[번호].필드: 사유`)
   - 글 수정의 기준 버전이 지금 버전과 다르면 → 409 `K003`, `data`에 지금 글
   - 대상 카드·연결이 이미 지워졌으면 → 그 이벤트만 무시하고 기록하지 않음
6. 반영한 이벤트마다 번호(`seq`)를 붙여 `canvas_event`에 기록한다.
7. 응답(`lastSeq`, `firstChangedLayer`, `textVersions`)을 `canvas_request`에 저장한다.
8. 커밋 후 전달용 알림(`CanvasEventsCommitted`)을 발행한다.

1~8은 한 트랜잭션이다. 중간에 실패하면 묶음 전체가 롤백된다(같은 묶음의 이동도 반영되지 않는다).

## 4. 결정 기록

각 항목: 문제 → 선택지 → 결정 → 이유.

### D1. 카드·연결 ID는 화면이 UUID로 만든다

- **문제**: 데모는 `c{n}`, `l{n}` 순번을 화면이 만든다. 두 사람이 동시에 카드를 만들면 같은 ID가 나온다.
- **선택지**: (a) 화면 순번 유지, (b) 서버가 발급하고 응답으로 알려 줌, (c) 화면이 UUID 생성
- **결정**: (c)
- **이유**: (b)는 서버 응답 전까지 화면이 카드를 가리킬 ID가 없어 "먼저 화면을 바꾸고 묶어 보낸다"는 흐름(150ms 묶음)과 맞지 않는다. UUID는 겹칠 확률이 사실상 없고 서버 왕복 없이 바로 쓸 수 있다.
- **지킬 것**: 화면이 보낸 ID가 다른 캔버스의 카드를 가리키지 못하도록 서버는 항상 (캔버스, ID)로 찾는다. 이미 있는 ID로 만들면 400.

### D2. 위치와 글을 다른 컬럼에 둔다

- **문제**: 한 사람이 카드를 옮기는 동안 다른 사람이 같은 카드의 프롬프트를 고치면, 카드를 통째로 저장하는 방식에서는 한쪽이 다른 쪽을 덮어쓴다.
- **결정**: 위치(`x`, `y`), 프롬프트 카드 본문(`text`), 카드 프롬프트(`prompt`), 종류별 필드(`props`)를 다른 컬럼에 두고, 이벤트마다 자기 컬럼만 바꾼다.
- **이유**: 서로 다른 칸을 고치는 동시 편집은 충돌이 아니다. 칸을 나누면 둘 다 남는다.

### D3. 같은 글을 동시에 고치면 버전 비교로 막는다 (409)

- **문제**: 화면은 글을 고칠 때 바뀐 부분이 아니라 글 전체를 보낸다. 두 사람이 같은 글을 거의 동시에 고치면, 나중에 저장한 사람이 먼저 저장한 사람의 수정을 모른 채 덮어써 한쪽 수정이 조용히 사라진다.
  ```
  현재 "감가상각비 추이 확인"(버전 3)
  A: "… 추이와 CapEx 비교" 저장 → 버전 4
  B: (버전 3을 보고 고침) "… 추이 확인, 출처 표기" 저장 → A의 "CapEx 비교"가 사라짐
  ```
- **대상**: 동시에 고칠 수 있는 글 3가지 — 프롬프트 카드 본문(`edit_prompt`), 카드 프롬프트(`set_card_prompt`), 선 프롬프트(`set_link_prompt`). 글마다 버전을 따로 둔다.
- **선택지**

  | 방식 | 장점 | 단점 |
  |---|---|---|
  | **버전 비교 + 409 (결정)** | 덮어쓰기를 막는다. 구현이 작다 | 늦게 저장한 사람이 최신 글을 보고 다시 합쳐야 한다 |
  | 나중 값이 이김 | 가장 단순 | 수정이 알림 없이 사라진다 |
  | 글자 단위 실시간 병합(OT·CRDT) | 자동으로 합쳐진다 | 구현이 크다. MVP 제외로 정함 |
  | 편집 중 잠금 | 충돌이 생기지 않는다 | 잠금 해제·시간 초과·끊김 처리가 필요하고, 다른 사람이 기다려야 한다 |

- **이유**: 프롬프트 글은 짧고, 같은 글을 같은 순간에 고칠 일은 드물다. 드물게 생기는 충돌만 알려 주면 되므로 버전 비교가 비용 대비 맞다.
- **규칙**: 이벤트는 고치기 시작한 버전을 `baseVersion`으로 보낸다. 지금 버전과 다르면 묶음 전체를 409 `K003`으로 거절하고 `data`에 `{ targetId, field, text, version }`(지금 글)을 담는다. 성공하면 응답 `textVersions`에 새 버전을 담는다.
- **위치는 비교하지 않는다**: 같은 카드를 두 사람이 옮기면 나중 위치가 이기는 것이 자연스럽고 잃는 정보가 없다.

### D4. 같은 캔버스의 요청은 캔버스 행 잠금으로 한 줄로 세운다

- **문제**: 이벤트 번호(`seq`)는 캔버스 안에서 겹치거나 빠지면 안 된다(받는 쪽이 빠진 번호로 누락을 알아챈다). 글 버전 비교도 동시에 들어온 두 요청이 같은 버전을 보고 둘 다 통과하면 안 된다.
- **선택지**: (a) 캔버스 행 비관적 잠금(`PESSIMISTIC_WRITE`), (b) 낙관적 잠금(`@Version`) 후 재시도, (c) DB 시퀀스로 번호만 발급
- **결정**: (a)
- **이유**: 한 묶음의 트랜잭션은 짧다(DB만, 외부 호출 없음). 잠금 대기가 짧아 재시도 로직(b)을 둘 이유가 없다. (c)는 번호에 빈칸이 생길 수 있고(롤백), 글 버전 경쟁은 막지 못한다. 잠금 하나로 번호와 버전 비교를 함께 지킨다.
- **확인**: 두 사람이 동시에 10묶음씩 보내도 번호가 겹치거나 빠지지 않는 테스트가 있다.

### D5. 재전송 중복은 처리한 묶음의 응답을 저장해 막는다

- **문제**: 화면은 응답을 못 받으면 같은 묶음을 다시 보낸다. 서버가 이미 저장했다면 두 번 반영된다(카드 두 장, 번호 낭비).
- **선택지**: (a) `canvas_request`에 (캔버스, `requestId`)와 응답을 저장, (b) 이벤트 로그의 `request_id`로 찾아 응답을 다시 계산
- **결정**: (a)
- **이유**: 응답에는 그때의 글 버전(`textVersions`)이 들어 있어 나중에 다시 계산하면 값이 달라질 수 있다. 저장해 두면 처음 응답과 정확히 같다. 모든 이벤트가 무시된 묶음(기록 0건)도 중복으로 알아챌 수 있다.

### D6. 한 묶음 안의 카드 이동은 카드별 마지막 위치만 저장한다

- **문제**: 드래그는 150ms마다 이동 이벤트를 만든다. 모두 저장하면 이벤트 로그가 빠르게 커지고 번호도 많이 쓴다.
- **결정**: 묶음 안에서 같은 카드의 `move_card`는 마지막 것만 저장한다. 다른 이벤트 순서는 그대로 둔다.
- **이유**: 중간 위치는 다시 쓸 일이 없다. 다른 사람에게 움직이는 모습은 커서 공유(5.6)와 묶음마다 오는 마지막 위치로 충분하다.

### D7. 시각화(`chart`) 카드도 저장한다 (`add_chart` 추가)

- **문제**: 프론트 명세에는 시각화 카드가 "화면 전용"이고 만드는 이벤트가 없다. 서버에 저장하지 않으면 새로고침·재접속 때 사라진다.
- **결정**: `add_chart`(`cardId`, `compareId`, `x`, `y`) 이벤트로 저장한다. 프롬프트 컨텍스트에는 넣지 않는다(층 영향 없음).
- **이유**: "새로고침·재접속·서버 재시작 뒤에도 상태가 복원된다"는 요구사항. 원본 비교 카드가 이미 지워졌으면 무시한다. 비교 카드가 나중에 지워지면 열 때 `warnings`로 알린다.

### D8. 활동 로그는 이벤트 기록에서 만들고, 공유 변경도 이벤트로 남긴다

- **선택지**: (a) 활동 로그 테이블을 따로 둠, (b) `canvas_event`에서 종류별 문구로 만듦
- **결정**: (b). 공유 명단 변경은 `set_share` 이벤트로 기록한다.
- **이유**: 같은 사실을 두 번 저장하지 않는다. 작성자는 이벤트를 보낸 인증 사용자로 이미 기록돼 있다. 공유 변경도 같은 번호 순서에 들어가야 받는 쪽이 번호 누락으로 오해하지 않는다.
- **규칙**: 이동·행 선택·정렬처럼 잦고 사소한 조작은 활동 로그에 보이지 않는다(기록은 남음). 최근 200건.

### D9. 이미 지워진 카드·연결을 가리키는 수정은 무시한다

- **문제**: A가 카드를 지운 직후, 아직 그 사실을 받지 못한 B가 같은 카드를 옮기거나 고친다.
- **선택지**: (a) 그 이벤트만 무시, (b) 묶음 전체를 오류로 거절
- **결정**: (a). 기록하지 않는다(번호도 쓰지 않음).
- **이유**: 카드가 이미 없으니 그 수정은 의미가 없다. 오류로 거절하면 B의 같은 묶음에 있던 다른 정상 수정까지 버려진다. B는 곧 삭제 이벤트를 받아 화면에서도 카드를 지운다.
- **예외**: 이미 있는 ID로 새로 만들기는 화면 버그라 400으로 거절한다.

### D10. 종류별 필드는 JSONB 한 컬럼에, 엔티티에서는 문자열로 다룬다

- **선택지**: (a) 카드 종류별 테이블, (b) 한 테이블 + JSONB `props`
- **결정**: (b). 엔티티는 JSONB를 문자열로 들고, 변환은 서비스(`CanvasJson`)가 한다.
- **이유**: 카드 종류가 화면 기획에 따라 자주 바뀐다(#97에서 메모 → 프롬프트, 대시보드 추가). 종류별 테이블이면 바뀔 때마다 마이그레이션이 필요하다. 종류별 필드는 검색 조건으로 쓰지 않으므로 JSONB로 충분하다.
- **문자열로 다루는 이유**: Spring Boot 4는 Jackson 3을 쓰는데, Hibernate의 JSON 변환기와의 버전 조합에 기대지 않으려고 변환을 직접 한다. `ddl-auto: validate`는 통과한다(테스트로 확인).

### D11. 소유자는 `canvas.owner_id`에만 둔다

- **이유**: 소유자는 한 명이고 바뀌지 않는다(소유권 넘기기는 MVP 밖). 공유 명단에 넣으면 "소유자를 명단에서 빼기·바꾸기"를 막는 규칙이 따로 필요하다. 분리해 두면 공유 명단 교체(`PUT /shares`)가 소유자를 건드릴 수 없다.

### D12. 캔버스 삭제는 표시만 한다

- **이유**: 그 캔버스로 만든 초안·질문·평가 결과는 남아야 한다(결과는 수정·삭제하지 않고 쌓는다). 행을 남기면 결과물이 참조를 잃지 않는다. 삭제된 캔버스는 없는 캔버스(404)로 다루고 목록에서 뺀다.

### D13. 인증 전에는 모든 캔버스 API가 401이다

- **문제**: #34(JWT)가 아직 없어서 "지금 사용자"를 알 수 없다.
- **선택지**: (a) 헤더의 사용자 ID를 그대로 믿는 임시 구현, (b) `CurrentUserProvider` 인터페이스 + 기본 구현은 항상 401(`A002`)
- **결정**: (b)
- **이유**: (a)는 배포되면 누구나 다른 사람으로 위장할 수 있다. 테스트는 가짜 구현을 쓰고, #34가 JWT 구현체를 빈으로 등록하면 기본 구현은 자동으로 빠진다(`@ConditionalOnMissingBean`).

### D14. 응답의 사람 정보는 지금 ID만 담는다

- **이유**: 이름·부서는 user 도메인(#34)이 갖는다. 다른 기능의 리포지토리를 직접 쓰지 않는다는 규칙 때문에 지금은 `{ "id": 2 }` 모양(`UserRef`)으로만 주고, #34 이후 user 서비스를 통해 이름을 채운다. 화면 모양은 바뀌지 않는다(필드 추가만).

### D15. `firstChangedLayer`는 이벤트 종류로 정한다 [제안]

| 층 | 이벤트 |
|---|---|
| `L1_sources` | `add_card`, `add_doc`, `add_dash`, `remove_card` |
| `L2_workspace` | `add_prompt`, `edit_prompt`, `set_card_prompt`, `set_link_prompt`, `add_rows`, `remove_row`, `create_compare`, `add_link`, `set_link`, `remove_link` |
| `L3_edits` | `edit_cell`, `revert_card`, `select_period`, `sort_card`, `confirm_mapping` |
| 영향 없음 | `move_card`, `add_chart` |

묶음 안에서 가장 앞 층을 돌려준다. ai의 컨텍스트 층 구성이 정해지면 맞춘다.

### D16. 마이그레이션 번호

- V9를 쓴다. #34도 users 컬럼 추가로 새 번호가 필요하다. 먼저 머지되는 쪽이 V9를 쓰고, 나중 쪽이 번호를 올린다(이미 적용된 마이그레이션은 고치지 않는다).

## 5. 커밋 후 알림 (#83 연결 지점)

| 알림 | 언제 | 받는 쪽(#83)이 할 일 |
|---|---|---|
| `CanvasEventsCommitted` | 이벤트 묶음 저장, 공유 변경(`set_share`) | `/topic/canvases/{id}/events`로 `firstSeq`·`lastSeq`·`events`·`textVersions` 전송 |
| `CanvasAccessChanged` | 공유 변경, 캔버스 삭제 | 권한이 사라진 사람의 구독 끊기, `/user/queue/canvases`로 개인 알림 |

서비스는 트랜잭션 안에서 발행만 한다. 받는 쪽은 `@TransactionalEventListener(AFTER_COMMIT)`으로 받아야 롤백된 변경을 보내지 않는다.
