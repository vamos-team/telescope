# 협업 캔버스 설계와 결정 기록

> 작성자 : 윤혜정 (이슈 #82, 실시간 전달 #83)

> 캔버스 도메인(`backend/.../canvas`)을 어떻게 저장하고, 여러 사람이 동시에 고칠 때 무엇을 지키는지와
> 그렇게 정한 이유를 남긴다. API 경로·필드는 `docs/frontend/api-spec.md` 3장, 공통 규약(권한, 저장 규칙,
> 실시간 연결)은 `docs/backend/api-spec.md` 4·5장, 실시간 전달 방식 선정은 같은 문서 11장을 따른다.

## 1. 범위

| 다룸 | 다루지 않음 |
|---|---|
| 캔버스 목록·생성·이름 변경·삭제·열기 (#82) | 화면 연동(#84) |
| 공유 명단(소유자·편집·보기) (#82) | 카드 태그·비교·컨텍스트 계산(ai), 공시·문서 조회(mcp-server) |
| 카드·연결 이벤트 저장, 글 충돌, 재전송 중복 방지 (#82) | 초안·질문·평가 결과물 |
| 활동 로그 (#82) | 인증 구현(#34) |
| 권한 확인(HTTP와 실시간 구독이 같은 서비스를 씀) (#82) | 여러 backend 인스턴스 간 실시간 방송 |
| 실시간 전달: 변경·커서·접속자·개인 알림 (#83, 6장) | |

## 3. 이벤트 묶음 처리 순서 (`CanvasEventService.apply`)

1. 캔버스 행을 잠그고 읽는다(`SELECT … FOR UPDATE`). 없거나 삭제됐으면 404.
2. 편집 권한(소유자·편집)을 확인한다. 아니면 403(`K001`/`K002`).
3. 같은 `requestId`를 이미 처리했으면 저장해 둔 응답을 그대로 돌려주고 끝낸다.
4. 같은 카드의 이동은 묶음 안에서 마지막 위치만 남긴다.
5. 이벤트를 순서대로 적용한다.
   - 형식 오류 → 400 `C001`(`events[번호].필드: 사유`)
   - 글 수정의 기준 버전이 지금 버전과 다르면 → 409 `K003`, `data`에 지금 글
   - 대상 카드·연결이 이미 지워졌으면 → 그 이벤트만 무시하고 기록하지 않음
6. 반영한 이벤트마다 번호(`seq`)를 붙여 `canvas_event`에 기록한다.
7. 응답(`lastSeq`, `firstChangedLayer`, `textVersions`)을 `canvas_request`에 저장한다.
8. 커밋 후 전달용 알림(`CanvasEventsCommitted`)을 발행한다.

1~8은 한 트랜잭션이다. 중간에 실패하면 묶음 전체가 롤백된다(같은 묶음의 이동도 반영되지 않는다).

## 4. 결정 기록

각 항목: 문제 → 선택지 → 결정 → 이유.

### D1. 카드·연결 ID는 화면이 UUID로 만든다

- **문제**: 데모는 `c{n}`, `l{n}` 순번을 화면이 만든다. 두 사람이 동시에 카드를 만들면 같은 ID가 나온다.
- **선택지**: (a) 화면 순번 유지, (b) 서버가 발급하고 응답으로 알려 줌, (c) 화면이 UUID 생성
- **결정**: (c)
- **이유**: (b)는 서버 응답 전까지 화면이 카드를 가리킬 ID가 없어 "먼저 화면을 바꾸고 묶어 보낸다"는 흐름(150ms 묶음)과 맞지 않는다. UUID는 겹칠 확률이 사실상 없고 서버 왕복 없이 바로 쓸 수 있다.
- **지킬 것**: 화면이 보낸 ID가 다른 캔버스의 카드를 가리키지 못하도록 서버는 항상 (캔버스, ID)로 찾는다. 이미 있는 ID로 만들면 400.

### D2. 위치와 글을 다른 컬럼에 둔다

- **문제**: 한 사람이 카드를 옮기는 동안 다른 사람이 같은 카드의 프롬프트를 고치면, 카드를 통째로 저장하는 방식에서는 한쪽이 다른 쪽을 덮어쓴다.
- **결정**: 위치(`x`, `y`), 메모 카드 본문(`text`), 카드 메모(`memo`, #123 전에는 프롬프트), 종류별 필드(`props`)를 다른 컬럼에 두고, 이벤트마다 자기 컬럼만 바꾼다.
- **이유**: 서로 다른 칸을 고치는 동시 편집은 충돌이 아니다. 칸을 나누면 둘 다 남는다.

### D3. 같은 글을 동시에 고치면 버전 비교로 막는다 (409)

- **문제**: 화면은 글을 고칠 때 바뀐 부분이 아니라 글 전체를 보낸다. 두 사람이 같은 글을 거의 동시에 고치면, 나중에 저장한 사람이 먼저 저장한 사람의 수정을 모른 채 덮어써 한쪽 수정이 조용히 사라진다.
  ```
  현재 "감가상각비 추이 확인"(버전 3)
  A: "… 추이와 CapEx 비교" 저장 → 버전 4
  B: (버전 3을 보고 고침) "… 추이 확인, 출처 표기" 저장 → A의 "CapEx 비교"가 사라짐
  ```
- **대상**: 동시에 고칠 수 있는 글 3가지 — 메모 카드 본문(`edit_memo`), 카드 메모(`set_card_memo`), 선 메모(`set_link_memo`). (#123 전 이름은 `*_prompt`) 글마다 버전을 따로 둔다.
- **선택지**

  | 방식 | 장점 | 단점 |
  |---|---|---|
  | **버전 비교 + 409 (결정)** | 덮어쓰기를 막는다. 구현이 작다 | 늦게 저장한 사람이 최신 글을 보고 다시 합쳐야 한다 |
  | 나중 값이 이김 | 가장 단순 | 수정이 알림 없이 사라진다 |
  | 글자 단위 실시간 병합(OT·CRDT) | 자동으로 합쳐진다 | 구현이 크다. MVP 제외로 정함 |
  | 편집 중 잠금 | 충돌이 생기지 않는다 | 잠금 해제·시간 초과·끊김 처리가 필요하고, 다른 사람이 기다려야 한다 |

- **이유**: 프롬프트 글은 짧고, 같은 글을 같은 순간에 고칠 일은 드물다. 드물게 생기는 충돌만 알려 주면 되므로 버전 비교가 비용 대비 맞다.
- **규칙**: 이벤트는 고치기 시작한 버전을 `baseVersion`으로 보낸다. 지금 버전과 다르면 묶음 전체를 409 `K003`으로 거절하고 `data`에 `{ targetId, field, text, version }`(지금 글)을 담는다. 성공하면 응답 `textVersions`에 새 버전을 담는다.
- **위치는 비교하지 않는다**: 같은 카드를 두 사람이 옮기면 나중 위치가 이기는 것이 자연스럽고 잃는 정보가 없다.

### D4. 같은 캔버스의 요청은 캔버스 행 잠금으로 한 줄로 세운다

- **문제**: 이벤트 번호(`seq`)는 캔버스 안에서 겹치거나 빠지면 안 된다(받는 쪽이 빠진 번호로 누락을 알아챈다). 글 버전 비교도 동시에 들어온 두 요청이 같은 버전을 보고 둘 다 통과하면 안 된다.
- **선택지**: (a) 캔버스 행 비관적 잠금(`PESSIMISTIC_WRITE`), (b) 낙관적 잠금(`@Version`) 후 재시도, (c) DB 시퀀스로 번호만 발급
- **결정**: (a)
- **이유**: 한 묶음의 트랜잭션은 짧다(DB만, 외부 호출 없음). 잠금 대기가 짧아 재시도 로직(b)을 둘 이유가 없다. (c)는 번호에 빈칸이 생길 수 있고(롤백), 글 버전 경쟁은 막지 못한다. 잠금 하나로 번호와 버전 비교를 함께 지킨다.
- **확인**: 두 사람이 동시에 10묶음씩 보내도 번호가 겹치거나 빠지지 않는 테스트가 있다.

### D5. 재전송 중복은 처리한 묶음의 응답을 저장해 막는다

- **문제**: 화면은 응답을 못 받으면 같은 묶음을 다시 보낸다. 서버가 이미 저장했다면 두 번 반영된다(카드 두 장, 번호 낭비).
- **선택지**: (a) `canvas_request`에 (캔버스, `requestId`)와 응답을 저장, (b) 이벤트 로그의 `request_id`로 찾아 응답을 다시 계산
- **결정**: (a)
- **이유**: 응답에는 그때의 글 버전(`textVersions`)이 들어 있어 나중에 다시 계산하면 값이 달라질 수 있다. 저장해 두면 처음 응답과 정확히 같다. 모든 이벤트가 무시된 묶음(기록 0건)도 중복으로 알아챌 수 있다.

### D6. 한 묶음 안의 카드 이동은 카드별 마지막 위치만 저장한다

- **문제**: 드래그는 150ms마다 이동 이벤트를 만든다. 모두 저장하면 이벤트 로그가 빠르게 커지고 번호도 많이 쓴다.
- **결정**: 묶음 안에서 같은 카드의 `move_card`는 마지막 것만 저장한다. 다른 이벤트 순서는 그대로 둔다.
- **이유**: 중간 위치는 다시 쓸 일이 없다. 다른 사람에게 움직이는 모습은 커서 공유(5.6)와 묶음마다 오는 마지막 위치로 충분하다.

### D7. 시각화(`chart`) 카드도 저장한다 (`add_chart` 추가) — #123에서 D26으로 바뀜

- **문제**: 프론트 명세에는 시각화 카드가 "화면 전용"이고 만드는 이벤트가 없다. 서버에 저장하지 않으면 새로고침·재접속 때 사라진다.
- **결정**: `add_chart`(`cardId`, `compareId`, `x`, `y`) 이벤트로 저장한다. 프롬프트 컨텍스트에는 넣지 않는다(층 영향 없음).
- **이유**: "새로고침·재접속·서버 재시작 뒤에도 상태가 복원된다"는 요구사항. 원본 비교 카드가 이미 지워졌으면 무시한다. 비교 카드가 나중에 지워지면 열 때 `warnings`로 알린다.

### D8. 활동 로그는 이벤트 기록에서 만들고, 공유 변경도 이벤트로 남긴다

- **선택지**: (a) 활동 로그 테이블을 따로 둠, (b) `canvas_event`에서 종류별 문구로 만듦
- **결정**: (b). 공유 명단 변경은 `set_share` 이벤트로 기록한다.
- **이유**: 같은 사실을 두 번 저장하지 않는다. 작성자는 이벤트를 보낸 인증 사용자로 이미 기록돼 있다. 공유 변경도 같은 번호 순서에 들어가야 받는 쪽이 번호 누락으로 오해하지 않는다.
- **규칙**: 이동·행 선택·정렬처럼 잦고 사소한 조작은 활동 로그에 보이지 않는다(기록은 남음). 최근 200건.

### D9. 이미 지워진 카드·연결을 가리키는 수정은 무시한다

- **문제**: A가 카드를 지운 직후, 아직 그 사실을 받지 못한 B가 같은 카드를 옮기거나 고친다.
- **선택지**: (a) 그 이벤트만 무시, (b) 묶음 전체를 오류로 거절
- **결정**: (a). 기록하지 않는다(번호도 쓰지 않음).
- **이유**: 카드가 이미 없으니 그 수정은 의미가 없다. 오류로 거절하면 B의 같은 묶음에 있던 다른 정상 수정까지 버려진다. B는 곧 삭제 이벤트를 받아 화면에서도 카드를 지운다.
- **예외**: 이미 있는 ID로 새로 만들기는 화면 버그라 400으로 거절한다.

### D10. 종류별 필드는 JSONB 한 컬럼에, 엔티티에서는 문자열로 다룬다

- **선택지**: (a) 카드 종류별 테이블, (b) 한 테이블 + JSONB `props`
- **결정**: (b). 엔티티는 JSONB를 문자열로 들고, 변환은 서비스(`CanvasJson`)가 한다.
- **이유**: 카드 종류가 화면 기획에 따라 자주 바뀐다(#97에서 메모 → 프롬프트, 대시보드 추가). 종류별 테이블이면 바뀔 때마다 마이그레이션이 필요하다. 종류별 필드는 검색 조건으로 쓰지 않으므로 JSONB로 충분하다.
- **문자열로 다루는 이유**: Spring Boot 4는 Jackson 3을 쓰는데, Hibernate의 JSON 변환기와의 버전 조합에 기대지 않으려고 변환을 직접 한다. `ddl-auto: validate`는 통과한다(테스트로 확인).

### D11. 소유자는 `canvas.owner_id`에만 둔다

- **이유**: 소유자는 한 명이고 바뀌지 않는다(소유권 넘기기는 MVP 밖). 공유 명단에 넣으면 "소유자를 명단에서 빼기·바꾸기"를 막는 규칙이 따로 필요하다. 분리해 두면 공유 명단 교체(`PUT /shares`)가 소유자를 건드릴 수 없다.

### D12. 캔버스 삭제는 표시만 한다

- **이유**: 그 캔버스로 만든 초안·질문·평가 결과는 남아야 한다(결과는 수정·삭제하지 않고 쌓는다). 행을 남기면 결과물이 참조를 잃지 않는다. 삭제된 캔버스는 없는 캔버스(404)로 다루고 목록에서 뺀다.

### D13. 인증 전에는 모든 캔버스 API가 401이다

- **문제**: #34(JWT)가 아직 없어서 "지금 사용자"를 알 수 없다.
- **선택지**: (a) 헤더의 사용자 ID를 그대로 믿는 임시 구현, (b) `CurrentUserProvider` 인터페이스 + 기본 구현은 항상 401(`A002`)
- **결정**: (b)
- **이유**: (a)는 배포되면 누구나 다른 사람으로 위장할 수 있다. 테스트는 가짜 구현을 쓰고, #34가 JWT 구현체를 빈으로 등록하면 기본 구현은 자동으로 빠진다(`@ConditionalOnMissingBean`).

### D14. 응답의 사람 정보는 지금 ID만 담는다

- **이유**: 이름·부서는 user 도메인(#34)이 갖는다. 다른 기능의 리포지토리를 직접 쓰지 않는다는 규칙 때문에 지금은 `{ "id": 2 }` 모양(`UserRef`)으로만 주고, #34 이후 user 서비스를 통해 이름을 채운다. 화면 모양은 바뀌지 않는다(필드 추가만).

### 6.2 결정 기록

#### D17. 공유가 풀린 사람은 "구독 끊기" 대신 "보내지 않기"로 막는다

- **문제**: 메모리 브로커(simple broker)는 서버가 특정 사람의 구독 하나를 끊는 방법을 주지 않는다. 연결 전체를 끊으면 그 사람이 열어 둔 다른 캔버스까지 끊긴다.
- **선택지**: (a) 연결 전체 끊기, (b) 권한 확인을 통과한 구독을 서버가 기록하고, 나가는 메시지마다 그 기록이 있는 세션에만 보냄
- **결정**: (b). 공유가 풀리면 기록에서 빼고 개인 알림(`revoked`)을 보낸다. 화면은 알림을 받고 구독을 푼다.
- **이유**: 다른 캔버스 연결에 영향이 없다. 나가는 필터는 메모리 조회라 커서처럼 잦은 메시지에도 부담이 적다(메시지마다 DB로 권한을 확인하지 않음).

#### D18. 커서는 보낸 사람에게도 가고, 화면이 자기 것을 무시한다

- **문제**: 규약 초안은 "보낸 사람에게는 다시 보내지 않는다"였다. 메모리 브로커는 주소 하나로 구독자 모두에게 보낸다.
- **선택지**: (a) 받는 사람마다 따로 보내 보낸 사람만 빼기, (b) 모두에게 보내고 화면이 `user.id`로 자기 것을 무시
- **결정**: (b)
- **이유**: 커서는 사람마다 초당 20번까지 온다. (a)는 서버가 받는 사람 수만큼 메시지를 만들어야 한다. (b)는 한 번만 보내고, 화면의 비교 한 줄로 끝난다.

#### D19. 권한 없는 구독은 STOMP `ERROR`로 거절한다 (연결이 닫힌다)

- **이유**: 권한 확인은 구독할 때 하는 것이 가장 확실하다. STOMP 규약상 `ERROR`를 보낸 연결은 닫힌다. 화면은 권한이 있는 캔버스만 구독하므로 정상 흐름에서는 생기지 않고, 공유가 풀린 직후처럼 드문 경우에만 다시 연결하면 된다.

#### D20. 커서 보내기는 그 캔버스를 구독 중인 연결만 받고, 50ms보다 잦으면 버린다

- **이유**: 커서마다 DB로 권한을 확인하지 않기 위해, 구독할 때 확인한 기록을 그대로 쓴다. 공유가 풀리면 기록이 빠지므로 커서도 더 보내지 못한다. 빈도 제한은 화면이 잘못 만들어져도 서버와 다른 사람이 메시지에 묻히지 않게 한다.
- **구독 기록이 없는 커서는 `ERROR` 없이 버린다**: 같은 연결의 프레임은 병렬로 처리돼, 구독 직후 보낸 커서가 구독 기록보다 먼저 확인될 수 있다. 이때 연결을 닫으면 권한 있는 사람도 다시 연결해야 한다. 커서는 곧 다음 위치가 오므로 한 번 버려도 된다.
- **수신 순서 보존(`setPreserveReceiveOrder`)은 쓰지 않는다**: 위 경우를 순서 보존으로 막아 보았으나, 켜면 인증·권한 거절이 `ERROR` 프레임으로 전달되지 않고 연결이 멈췄다(통합 테스트로 확인). 나가는 메시지의 발행 순서 보존(`setPreservePublishOrder`)은 켠다.

#### D21. 인증 기본 구현은 자동 설정으로 등록한다

- **문제**: 일반 설정 클래스의 `@ConditionalOnMissingBean`은 평가 순서가 보장되지 않는다. 실제로 테스트용 토큰 검증기를 등록했을 때 기본 구현과 함께 두 개가 등록돼 앱이 뜨지 않았다. #34가 JWT 구현을 붙일 때도 같은 일이 생긴다.
- **결정**: `AuthConfig`를 자동 설정(`@AutoConfiguration` + `META-INF/spring/…AutoConfiguration.imports`)으로 등록한다.
- **이유**: 자동 설정은 사용자 빈이 모두 등록된 뒤 평가되므로, #34가 `CurrentUserProvider`·`AccessTokenVerifier` 구현을 빈으로 등록하기만 하면 기본 구현은 확실히 빠진다.

#### D22. 접속자 목록은 구독으로 한 번 받는다 (`/app/canvases/{id}/presence`)

- **이유**: 들어옴·나감만으로는 내가 들어오기 전부터 있던 사람을 모른다. 앱 주소 구독은 그 순간의 목록을 한 번만 돌려주고 끝나므로, 따로 HTTP API를 두지 않아도 된다. 한 사람이 창을 여러 개 열어도 한 번만 센다.

### 6.3 확인 (`CanvasRealtimeTest`)

실제 WebSocket(STOMP) 클라이언트로 붙어 확인한다. 구독 등록은 시간이 아니라 브로커의 구독 목록을 조회해 기다린다.

- 커밋된 묶음은 권한자 모두에게 가고, 롤백된 묶음(글 충돌)은 가지 않는다
- 토큰이 없거나 틀리면 연결이 거절된다
- 권한 없는 사람의 구독은 거절되고 메시지를 받지 못한다
- 커서는 같은 캔버스 구독자에게 보낸 사람 ID와 함께 간다
- 공유가 풀리면 개인 알림을 받고 이후 변경은 받지 못한다
- 접속자 들어옴·나감, 처음 구독 시 지금 목록

## 7. 프롬프트를 메모로 (#123)

화면(PR #122, #107)에서 프롬프트를 메모 하나로 통일하고, 선 관계 종류를 없애고, 시각화 카드를 공시 표에서 바로 만들게 바꿨다.
backend를 화면 규약(`docs/frontend/api-spec.md` 3.5·3.6)에 맞췄다. 바뀐 것은 `api-spec.md` 5.3에 정리했고, 아래는 backend에서 정한 것이다.

전제: 로그인(#34) 전이라 모든 캔버스 API가 `401`이다(D13). 배포·개발 DB 어디에도 실제 캔버스 데이터가 없다. 그래서 옛 데이터 처리는 "안전하게 옮기기"보다 "규약을 한 가지로 정리하기"를 기준으로 골랐다.

#### D23. 이름만 바꾸고 동작은 그대로 둔다

- 프롬프트 카드 → 메모 카드(`kind: memo`), 카드·선 프롬프트 → 카드·선 메모(`memo`, `memoVersion`), 이벤트 `*_prompt` → `*_memo`, 409 `field: memo`.
- 버전 비교(D3), 위치·글 분리(D2), 지워진 대상 무시(D9)는 그대로다. 글의 의미만 "작성 지시"에서 "사용자가 쓴 글"로 넓어졌고(분석에서 에이전트가 지시·근거·의견으로 가림), 저장 방식은 같다.
- 옛 이름(`add_prompt` 등)은 `400 C001 "알 수 없는 이벤트"`로 거절한다. 두 이름을 함께 받는 호환 코드는 두지 않았다. 화면이 새 이름만 보내고(PR #122), 서버에 옛 이름으로 저장된 실제 데이터가 없다.

#### D24. 연결 관계 종류(`rel`)는 칼럼째 지운다

| 후보 | 판단 |
|---|---|
| **(a) 칼럼 삭제** (선택) | 관계 종류는 분석에서 에이전트가 판단하기로 했으므로 저장할 이유가 없다. 실제 데이터가 없어 잃을 것도 없다. 쓰지 않는 칼럼을 남기지 않는다 |
| (b) NULL 허용으로 남김 | 다시 쓸 일이 생기면 바로 쓸 수 있지만, 그동안 아무도 쓰지 않는 칼럼이 남고 엔티티·응답에 의미 없는 필드가 생긴다 |

- `set_link` 이벤트도 없앴다. 예전 화면이 `add_link`에 `rel`을 보내면 오류 대신 무시한다(연결 자체는 유효하므로).

#### D25. 이벤트 기록의 옛 이름도 새 이름으로 바꾼다 (불변 원칙의 예외)

| 후보 | 판단 |
|---|---|
| (a) 상태 테이블만 바꾸고 이벤트 기록은 그대로 | "이벤트 기록은 고치지 않고 쌓는다"(루트 `CLAUDE.md` 4번)를 지킨다. 대신 활동 로그·변경 받기에서 옛 이름이 그대로 보인다 |
| **(b) 이벤트 기록도 새 이름으로** (선택, 사용자 결정) | 기록과 규약이 한 가지 이름으로 맞는다. 활동 로그 문구와 컨텍스트 층 대응표가 옛 이름을 몰라도 된다 |
| (c) 읽을 때 옛 이름을 새 이름으로 변환 | 기록은 그대로 두면서 보이는 이름을 맞추지만, 실제 데이터가 없는데 변환 코드가 계속 남는다 |

- 불변 원칙은 "기록한 사실(누가 언제 무엇을 했는지)을 바꾸지 않는다"는 뜻으로 보고, 이번은 같은 조작의 **이름만** 바꾸는 일이라 예외로 뒀다. 순번(`seq`)·작성자·시각·내용은 그대로다.
- `type` 칼럼과 `payload` 안의 `type`을 함께 바꾼다(`V12`). `add_chart`·`set_link` 기록은 새 이름에 대응하는 것이 없어 그대로 둔다(활동 로그에는 문구가 없어 보이지 않는다).
- 저장해 둔 묶음 응답(`canvas_request.response`)의 `textVersions` 키(`prompt`)는 바꾸지 않았다. 같은 `requestId` 재전송에만 쓰이고, 그런 옛 요청이 다시 올 일이 없다.

#### D26. 시각화 카드는 `create_compare`(`view: chart`)로 만들고 원본 표를 직접 가리킨다

- 이전(D7): `add_chart`(`compareId`)로 비교 카드에서만 만들고, 비교 카드를 가리켰다.
- 지금: 비교 카드와 같은 `create_compare`에 `view: chart`를 붙여 만든다. 카드에 원본 표 목록(`sources`)을 저장하고 비교와 같은 계산을 쓴다. 비교 카드 없이 공시 표에서 바로 만들 수 있다.
- 결과: 비교 카드를 지워도 시각화 카드는 남는다. 원본 표를 지우면 비교·시각화 카드 모두의 `sources`에서 뺀다. 복원 경고도 두 카드를 같은 규칙(원본 표가 있는지)으로 본다.
- `V12`는 비교 카드에서 만든 기존 시각화 카드에 그 비교의 `sources`를 옮겨 넣는다(`compareId`는 남겨 둠). 비교 계산 API는 아직 backend에 없어(화면 로컬 계산) 계산 위치는 이번에 정하지 않았다.
- `view`는 `compare`(기본)·`chart`만 받는다. 다른 값은 `400`.

#### D27. 선 메모 작성자(`memoBy`)는 마지막으로 고친 사람이다

| 후보 | 판단 |
|---|---|
| **(a) 마지막으로 고친 사람, 지우면 비움** (선택) | 화면 로컬 동작(`set_link_memo`를 보낸 사람)과 같다. 지금 보이는 글을 쓴 사람이 표시된다 |
| (b) 처음 쓴 사람 | 다른 사람이 내용을 바꿔도 처음 쓴 사람이 표시되어 글과 이름이 어긋날 수 있다 |

- `canvas_link.memo_by`(FK `users`). 캔버스 열기 응답 `links[].memoBy: { id }`, 메모가 없으면 `null`.
- 카드 메모에는 작성자를 두지 않았다. 화면이 선 메모에만 작성자를 표시한다.

#### D28. 계정 대응 취소(`accepted: null`)는 대응 기록을 지운다

- 화면은 확정·거부를 되돌릴 때 `accepted: null`을 보낸다(#123 표에는 없었지만 화면 규약 3.6에 있음). 이전에는 `true`/`false`만 받아 서버 모드에서 `400`이 났다.
- 화면 로컬 동작과 같게 그 (캔버스, 개념, 회사)의 대응 기록을 지운다. `canvas_mapping.accepted`는 그대로 `NOT NULL`이라 스키마 변경이 없다.
- 지울 기록이 없으면 반영한 것이 없으므로 이벤트를 기록하지 않는다(D9와 같은 기준).

#### 확인

- `CanvasEventServiceTest`: 이름 바뀐 이벤트 전체, 선 메모 작성자(고친 사람·지우면 비움), `rel` 무시, 메모 카드 종류와 카드 메모 거절, `view: chart` 생성(없는 원본 빼기, 잘못된 `view` 거절), 비교 카드 삭제 뒤 시각화 유지·원본 표 삭제 시 `sources`에서 제외, 옛 이벤트 이름 거절, 대응 취소
- `CanvasMemoMigrationTest`: 임시 스키마를 V11까지 올려 예전 모양의 카드·연결·이벤트를 넣고 V12를 적용 → 카드 종류·칼럼 이름·시각화 `sources`·`rel` 삭제·`memo_by`·이벤트 이름(칼럼과 `payload` 모두) 확인
