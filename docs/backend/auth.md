# 로그인 실패 잠금 설계와 결정 기록

> 이슈 #164. 응답 규약(오류 코드 `A006`, 공개 경로)은 `docs/backend/api-spec.md` 2·3장, 테이블은 `docs/erd/entities.md` 4.1을 따른다.

## 1. 목적과 범위

관리자 계정을 포함한 모든 계정을 비밀번호 대입 공격에서 지키려고, 같은 사번으로 연속해서 틀리면 일정 시간 로그인을 막는다.

| 다룸 | 다루지 않음 |
|---|---|
| 사번별 연속 실패 횟수, 잠금, 자동 해제 | IP별 횟수 제한 |
| 없는 사번도 같은 방식으로 세기 | 관리자가 잠금을 직접 푸는 기능 |
| 잠금 응답(`429` `A006`, `Retry-After`) | 회원가입 횟수 제한, CAPTCHA |
| | 화면 문구(frontend 담당, 협의 필요) |

## 2. 규칙 (결정 2026-11-27)

| 항목 | 값 | 설정 |
|---|---|---|
| 잠그는 연속 실패 횟수 | 5회 | `app.auth.login.max-failures` ← `AUTH_LOGIN_MAX_FAILURES` |
| 잠금 시간 | 10분 | `app.auth.login.lock-duration` ← `AUTH_LOGIN_LOCK_DURATION` (ISO-8601, 예: `PT10M`) |

1. 사번은 앞뒤 공백을 지운 값으로 센다.
2. 잠겨 있으면 비밀번호를 비교하지 않고 `429` `A006`을 돌려준다. 잠긴 동안은 맞는 비밀번호도 거절한다.
3. 비밀번호가 틀리면(없는 사번, 72바이트 초과 비밀번호 포함) 횟수를 하나 올린다. **5번째 실패의 응답은 `A001`**이고 이때 잠금 시각(지금 + 10분)을 정한다. 6번째 시도부터 `A006`이다.
4. 로그인에 성공하면 횟수를 0으로 되돌린다. 행은 지우지 않는다.
5. 잠금 시각이 지나면 자동으로 풀린다. 그 뒤 다시 틀리면 1부터 센다.
6. `Retry-After`는 남은 시간을 초로 올림한 값이다(최소 1). 0.2초 남았어도 1초로 알려 바로 다시 시도해 거절되지 않게 한다.

## 3. 저장 (`login_attempt`, `V15__create_login_attempt.sql`)

| 컬럼 | 설명 |
|---|---|
| `employee_no` PK | 사번. `users`와 FK 없음 |
| `failed_count` | 연속 실패 횟수 |
| `locked_until` | 잠금 해제 시각. 잠기지 않았으면 NULL |

- **DB에 둔 이유**: 서버를 다시 켜도 잠금이 유지되어야 한다. 메모리에 두면 재시작으로 잠금을 풀 수 있다.
- **FK를 두지 않은 이유**: 없는 사번도 같은 횟수에서 같은 응답으로 잠겨야 응답만 보고 사번이 있는지 알 수 없다.
- **성공 시 행을 남기고 0으로 되돌리는 이유**: 일반적인 계정 잠금 구현(실패 횟수 컬럼 초기화)과 같은 방식이다. 갱신 쿼리 하나로 처리되고, 마지막 시도 시각(`updated_at`)이 남아 추적에 쓸 수 있다.

## 4. 구현에서 지킨 것

| 문제 | 처리 |
|---|---|
| 로그인 실패 예외와 함께 실패 기록이 되돌려짐 | 기록은 `LoginAttemptService.recordFailure`가 새 트랜잭션(`REQUIRES_NEW`)에서 바로 커밋한다. `AuthService`와 다른 빈이라 트랜잭션 프록시를 거친다. `AuthService.login`에는 트랜잭션을 걸지 않는다 |
| 같은 사번으로 동시에 틀리면 횟수가 빠짐 | PostgreSQL `INSERT … ON CONFLICT (employee_no) DO UPDATE` 한 문장으로 올린다. 처음 실패하는 사번은 잠글 행이 없어 행 잠금(`SELECT … FOR UPDATE`)으로는 막을 수 없다 |
| 잠금 확인을 동시에 통과한 요청이 늦게 실패를 기록 | 이미 잠겨 있으면 잠금 시각을 늘리지 않는다 |
| 네이티브 쿼리에 `app` 스키마가 붙지 않음 | `{h-schema}`를 붙인다(`hibernate.default_schema`는 JPQL에만 적용됨) |
| 시각 테스트 | 주입받은 `Clock`으로 현재 시각을 구한다. 테스트는 시각을 앞으로 돌려 만료를 확인한다 |

## 5. 상태 코드로 429를 고른 이유

- `401`(`A001`)과 다르게, 사번·비밀번호가 맞아도 지금은 안 된다는 뜻이고 **기다리면 풀린다**. `429 Too Many Requests`와 `Retry-After`가 이 의미에 맞고, 클라이언트가 남은 시간을 표준 헤더로 읽을 수 있다.
- `423 Locked`는 WebDAV 자원 잠금용이라 쓰지 않았다. `403`은 권한 문제로 읽혀 쓰지 않았다.

## 6. 알고 받아들인 한계

- **남의 사번을 알면 그 사람을 10분씩 잠글 수 있다.** 사번은 사내에서 쉽게 알 수 있는 값이다. 관리자 계정 보호를 우선해 받아들였다. 문제가 되면 IP별 제한이나 관리자 잠금 해제를 따로 검토한다.
- 아무 사번이나 넣어 시도하면 `login_attempt`에 행이 쌓인다. IP 제한이 범위 밖이라 지금은 막지 않는다.
- 잠금 응답은 비밀번호를 비교하지 않아 응답이 빠르다. 하지만 없는 사번도 똑같이 잠기므로 이것으로 사번 존재 여부를 알 수는 없다.
