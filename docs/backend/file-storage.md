# 파일 저장소 (`infra/storage`)

> 작성자 : 윤혜정

> 사용자가 올린 원본 파일(예산서, 근거자료)을 저장하고 읽는 부분이다. 이슈 #10(로컬 구현), #89(S3 구현, PR #108) 기준.
> 코드가 바뀌면 이 문서도 함께 고친다.

## 1. 역할

- 사용자 업로드 원본을 저장하고, 키(`fileStorageKey`)로 다시 읽거나 지운다.
- 배포에서는 S3, 로컬에서는 디스크 폴더에 저장한다. 기능 패키지는 `FileStorage` 인터페이스만 안다.
- **공시 같은 공용 문서 원본은 여기에 저장하지 않는다.** 공용 문서 원본은 ai 쪽이 보관한다(`ai-contract.md` 2.11).
- ai/server는 같은 키로 S3(배포) 또는 같은 폴더(로컬)에서 원본을 읽는다(`ai-server-design.md` 2.6.1).

## 2. 구성

| 클래스 | 역할 |
|---|---|
| `FileStorage` | 인터페이스. `store`(저장 후 키 반환), `load`(키로 읽기, 없으면 `UncheckedIOException`), `delete`(없는 키도 예외 없음) |
| `LocalFileStorage` | 디스크 폴더(`FILE_STORAGE_DIR`, 기본 `./data/files`)에 저장. 키가 폴더 밖을 가리키면 거절 |
| `S3FileStorage` | S3 버킷(`S3_BUCKET`) 최상위에 저장 |
| `FileStorageConfig` | 둘 중 하나만 빈으로 등록(3.2) |
| `StorageKeys` | 키 생성 규칙 `<UUID><원본 확장자>` (예: `3f…9a.pdf`). 두 구현이 같이 쓴다 |

설정 (`application.yml` `app.storage`):

| 설정 | 환경변수 | 설명 |
|---|---|---|
| `local.base-dir` | `FILE_STORAGE_DIR` | 로컬 저장 폴더 |
| `s3.bucket` | `S3_BUCKET` | 값이 있으면 S3를 쓴다. 배포는 `s3-config` ConfigMap이 넣는다 |
| `s3.region` | `AWS_REGION` | 버킷이 있으면 필수 |

자격증명은 AWS SDK 기본 체인을 쓴다. 배포에서는 IRSA(`s3-access` 서비스 계정)로 키 없이 들어온다. 키를 코드·설정에 넣지 않는다.

## 3. 결정 기록 (#89)

### D1. AWS SDK v2는 BOM 2.58.0으로 고정한다

| 후보 (2026-11-26 기준) | 배포일 | 판단 |
|---|---|---|
| 2.59.10 | 11-25 | 최신. 배포 직후라 문제가 알려지기 전일 수 있다 |
| 2.59.0 | 11-12 | 2.59 계열 첫 버전 |
| **2.58.0** (선택) | 11-11 | 배포 2주가 지났다 |

- **고른 이유**: S3·STS 기본 기능(`putObject`, `getObject`, `deleteObject`, 웹 ID 토큰 자격증명)은 세 버전 사이에 차이가 없다. 그렇다면 배포 직후 버전을 피하는 쪽이 안전하다. ai/server의 boto3(1.44.0, 11-10)도 같은 기준으로 골랐다.
- `software.amazon.awssdk:bom`으로 버전을 한 곳에 두고 `s3`, `sts`는 버전 없이 쓴다(루트 `CLAUDE.md` 6번 "버전을 명시적으로 고정").
- **`sts`를 넣는 이유**: 없으면 IRSA의 웹 ID 토큰을 자격증명으로 바꾸지 못한다(인프라 안내).
- **확인한 근거**: 빌드된 jar 안에 `s3-2.58.0.jar`, `sts-2.58.0.jar`가 들어간 것을 확인했다.

### D2. 구현체는 `S3_BUCKET` 값이 있는지로 고른다

| 후보 | 장점 | 단점 |
|---|---|---|
| **(a) `S3_BUCKET`이 있으면 S3, 없으면 로컬** (선택) | 배포 ConfigMap(`s3-config`)에 이미 값이 있어 infra 변경이 없다. 로컬은 값이 없으니 자동으로 디스크를 쓴다 | 버킷 값을 실수로 비우면 배포에서도 조용히 로컬 디스크에 저장된다 |
| (b) `APP_STORAGE_TYPE=local\|s3`을 명시 | 의도가 분명하다 | 배포 ConfigMap에 값을 추가해야 해서 infra와 협의가 필요하다 |

- **고른 이유**: (a)의 단점은 "버킷이 없으면 S3를 쓸 수 없다"는 사실과 같아서, 따로 스위치를 두어도 막아 주는 것이 크지 않다. 대신 버킷은 있는데 리전이 비면 기동을 멈춰 잘못된 설정을 바로 알린다.
- **조건 클래스를 직접 둔 이유**: `S3_BUCKET:`의 기본값은 빈 문자열이다. 그런데 `@ConditionalOnProperty`는 빈 문자열도 "값 있음"으로 본다. 그래서 `StringUtils.hasText`로 확인하는 조건(`S3BucketConfigured` / `S3BucketNotConfigured`)을 두었다.
- **`LocalFileStorage`의 `@Component`를 없앤 이유**: 조건 없이 늘 등록되면 S3를 고른 배포에서도 `FileStorage` 빈이 둘이 된다. 두 구현 모두 `FileStorageConfig`에서만 등록한다.
- **확인한 근거**: 버킷 없음, 빈 값, 버킷과 리전 있음, 리전 누락 네 경우를 `ApplicationContextRunner`로 테스트했다. `S3_BUCKET` 없이 로컬 기동해 `/actuator/health` 200도 확인했다.

### D3. S3 구현 테스트는 `S3Client` 목으로 한다

| 후보 | 장점 | 단점 |
|---|---|---|
| **(a) `S3Client` 목(Mockito)** (선택) | 의존성 추가가 없고 빠르다. `backend/CLAUDE.md` "외부 연동은 Stub으로 테스트" 규칙에 맞다 | 실제 S3 동작(권한, 네트워크)은 보지 못한다 |
| (b) Testcontainers LocalStack | 실제에 가까운 S3로 저장·읽기·삭제를 본다 | localstack 모듈 의존성과 Docker 이미지가 추가된다 |

- **고른 이유**: 이 구현은 SDK 호출 세 개를 감싼 얇은 계층이라, 확인할 것은 "버킷·키를 맞게 넘기는지, 없는 키를 규약대로 바꾸는지"다. 목으로 충분하다.
- **남은 확인**: 실제 S3 저장·읽기는 배포 후 클러스터에서 확인한다(노트북에는 S3 자격증명이 없다).

### D4. `load`는 S3 응답을 스트림 그대로 돌려준다

| 후보 | 장점 | 단점 |
|---|---|---|
| **(a) 스트림** (선택) | 디스크를 쓰지 않고, 큰 파일도 메모리에 다 올리지 않는다 | 한 번만 읽을 수 있다. 호출자가 끝까지 읽거나 닫아야 연결이 반환된다 |
| (b) 임시 파일로 받아 `FileSystemResource` | 여러 번 읽을 수 있다 | 디스크를 쓰고, 임시 파일을 언제 지울지 호출자와 약속해야 한다 |

- **고른 이유**: backend가 원본을 여러 번 읽을 일은 지금 없다(파싱은 ai/server가 직접 S3에서 받는다).
- **`contentLength`를 S3 응답에서 가져오는 이유**: `InputStreamResource`의 기본 `contentLength()`는 스트림을 끝까지 읽어 길이를 잰다. 그러면 정작 내용을 읽을 수 없게 된다. 그래서 응답 헤더의 길이를 쓰도록 덮어썼다.

### D5. `store`는 임시 파일을 거쳐 올린다

- S3 업로드(`RequestBody`)는 길이를 미리 알아야 한다. 길이를 모르는 스트림을 그대로 넘기면 SDK가 메모리에 다 올려 길이를 잰다.
- 업로드 파일은 클 수 있으므로, 임시 파일에 먼저 받은 뒤 `RequestBody.fromFile`로 올린다. 임시 파일은 성공·실패와 관계없이 지운다.
- 버린 대안: 멀티파트 업로드(`S3TransferManager`)는 비동기 클라이언트와 추가 의존성이 필요해 MVP에서 쓰지 않았다.

### D6. 키 형식은 로컬과 S3가 같다

- `StorageKeys.newKey`로 `<UUID><원본 확장자>`를 만든다. 원본 파일명은 확장자만 쓰고 경로에 쓰지 않는다(경로 탈출 방지).
- 같은 형식이라 구현체를 바꿔도 키 모양이 같다. ai/server도 확장자를 보고 파서를 고르므로 확장자를 남긴다.
- S3에서는 버킷 최상위 키다. 폴더(접두어)는 두지 않았다. 문서 보관·삭제 정책(루트 `CLAUDE.md` 7장)이 정해지면 캔버스별 접두어 등을 다시 검토한다.

### D7. 원본은 사용자 업로드만 이 저장소에 둔다

- 결정(2026-11-26): 배포에서 S3에는 사용자 입력 파일만 두고, 공시 원본은 ai 쪽이 둔다. 근거와 영향은 `ai-contract.md` 2.11.
- 그래서 이 저장소에는 공용 문서를 올리는 경로를 만들지 않는다.

## 4. 알려진 한계

| 문제 | 영향 | 비고 |
|---|---|---|
| 업로드 원본을 언제 지울지 정해지지 않았다 | S3에 계속 쌓인다 | 문서 보관·삭제 정책(루트 `CLAUDE.md` 7장) |
| 실제 S3 동작은 클러스터에서만 확인할 수 있다 | 목 테스트는 권한·네트워크 문제를 못 잡는다 | 업로드 API(#111) 배포 후 확인 |
| `LocalFileStorage` 기본 경로는 실행 위치 기준 상대 경로다 | 컨테이너에서 기본값을 그대로 쓰면 의도와 다른 곳에 쓸 수 있다 | 클래스 주석의 TODO 참고. ai/server는 같은 이유로 기본값을 두지 않았다 |
