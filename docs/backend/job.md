# job 도메인

> 작성자 : 윤혜정

> 오래 걸리는 작업(자료 준비, 분석, 예측)의 상태를 저장하고 폴링으로 조회하는 부분이다. 이슈 #35 기준.
> 코드가 바뀌면 이 문서도 함께 고친다. 6~8번(문제, 확장, 재확인 시점)은 특히 자주 확인한다.

## 1. 역할

- 자료 준비, 분석, 예측은 수 초~수 분이 걸려 한 번의 요청으로 끝낼 수 없다. 요청하면 `jobId`를 돌려주고, 클라이언트가 `GET /api/v1/jobs/{id}`로 상태를 확인한다(폴링). 콜백은 없다.
- 실제 작업은 ai 서비스가 수행하고, backend는 그 **상태의 사본**을 `job` 테이블에 둔다. 이 도메인은 그 사본을 안전하게 저장하고 최신으로 맞추는 일을 맡는다.
- `Job`은 대상(`DocumentVersion`/`AnalysisRun`/`PredictionRun`)을 모른다. 대상이 `jobId`로 `Job`을 가리킨다.

## 2. 구성

```
job/
├── entity/      Job, JobType, JobStatus
├── repository/  JobRepository
├── service/     JobService
├── controller/  JobController
└── dto/         JobResponse
```

연관 코드: `infra.python.AiJobStatus`·`AiJobNotFoundException`(ai 쪽 상태와 예외), `global.config.ClockConfig`(시각 주입), `ErrorCode.JOB_INVALID_TRANSITION`(`J001`, 409)

## 3. 구현

### 3.1 상태 전이

```
QUEUED ──▶ RUNNING ──▶ SUCCEEDED
   │          │
   └──────────┴──────▶ FAILED
```

| 현재 | 갈 수 있는 상태 |
|---|---|
| `QUEUED` | `RUNNING`, `FAILED` |
| `RUNNING` | `SUCCEEDED`, `FAILED` |
| `SUCCEEDED`, `FAILED` | 없음 (종료 상태) |

규칙은 `JobStatus.canTransitionTo`가 갖고, `Job`이 상태를 바꿀 때마다 검사한다. 위반하면 `BusinessException(J001)`이다.

### 3.2 Job 엔티티

컬럼은 `V3__create_job.sql`, `V10__add_job_result_save_failures.sql`과 같다: `jobType`, `status`, `externalJobId`, `errorMessage`, `startedAt`, `finishedAt`, `resultSaveFailures`(결과 저장 실패 횟수, #63).

`@Setter`가 없다. 상태가 바뀌는 길을 아래 메서드로만 열어, 모든 변경이 전이 규칙을 지나가게 한다.

| 메서드 | 하는 일 |
|---|---|
| `Job.create(jobType)` | 새 작업을 `QUEUED`로 만든다 (정적 팩토리) |
| `start(now)` | `QUEUED → RUNNING`, `startedAt` 기록 |
| `succeed(now)` | `RUNNING → SUCCEEDED`, `finishedAt` 기록 |
| `fail(message, now)` | `QUEUED/RUNNING → FAILED`, `errorMessage`와 `finishedAt` 기록 |
| `assignExternalJobId(id)` | ai 서비스가 발급한 작업 ID 저장 |
| `isTerminal()` | 종료 상태인지 확인 |
| `syncFrom(status, message, now)` | ai가 알려 준 상태를 반영 |
| `recordResultSaveFailure(max, message, now)` | 결과 저장 실패를 한 번 센다. 한도에 닿으면 `FAILED`. 이미 끝났으면 무시 |
| `transitionTo(next)` (private) | 전이를 검사하고 상태를 바꾼다. `start/succeed/fail`이 모두 거친다 |

**`syncFrom`**: `start/succeed/fail`은 허용되지 않은 전이면 예외를 던진다. 폴링으로 받는 ai 상태는 같은 값이 반복되거나 단계를 건너뛰는 것이 정상이라 별도로 처리한다.

| ai가 알려 준 상태 | 처리 |
|---|---|
| 현재와 같은 상태 | 무시 |
| 이미 종료된 작업 | 무시 |
| `QUEUED` | 되돌리지 않고 무시 |
| `RUNNING` | `start` |
| `SUCCEEDED` (현재 `QUEUED`) | `start` 후 `succeed` (`startedAt`도 기록) |
| `FAILED` | `fail` |

### 3.3 JobService

| 메서드 | 용도 |
|---|---|
| `create(jobType)` | `QUEUED` 작업 생성 |
| `markStarted(jobId, externalJobId)` | ai 시작 요청이 성공했을 때. 외부 ID 저장 후 `RUNNING` |
| `markFailed(jobId, message)` | ai 시작 요청이 실패했을 때 |
| `getJob(jobId)` | 상태 조회. 미종료 작업이면 ai 상태를 받아 저장한 뒤 반환 |
| `isFinished(jobId)`, `unfinishedJobIds(jobType)`, `peek(jobIds)` | 저장된 상태만 읽는다(ai 호출 없음). 화면이 폴링하지 않는 배치(데이터 적재 #135)를 서버가 확인할 때와 목록 화면에 쓴다 |

**다른 도메인이 작업을 시작하는 순서**

1. 트랜잭션 1: 대상 저장과 `create`를 함께 커밋
2. 트랜잭션 밖: `PythonAiClient.startXxx` 호출
3. 트랜잭션 2: 성공하면 `markStarted`, 실패하면 `markFailed`

**`getJob`의 동작 (조회할 때 갱신)**

1. 작업 조회 (짧은 트랜잭션)
2. 종료됐거나 `externalJobId`가 없으면 그대로 반환 (ai 호출 없음)
3. `PythonAiClient.getJobStatus` 호출 (트랜잭션 밖)
4. 작업 행을 잠그고(`findByIdForUpdate`) 다시 읽어 반영한 뒤 반환 (짧은 트랜잭션)
   - ai가 `SUCCEEDED`: 아래 **결과 저장 후 완료**
   - 그 밖의 상태: `syncFrom`으로 반영

**결과 저장 후 완료 (#63)**

ai가 `SUCCEEDED`를 알려 주면, 대상 도메인이 결과를 저장하는 데 성공했을 때만 작업을 완료로 확정한다.

1. 한 트랜잭션에서 작업 행을 잠그고 다시 읽는다. 이미 끝났으면(다른 요청이 먼저 처리) 아무것도 하지 않는다. 그래서 결과가 두 번 저장되지 않는다.
2. 작업 종류의 `JobResultHandler`가 `result`를 저장한다.
3. 같은 트랜잭션에서 `syncFrom(SUCCEEDED)`로 완료한다.
4. 2~3이 실패하면 전부 되돌린다. 새 트랜잭션에서 `resultSaveFailures`만 1 올리고 작업은 진행 중으로 남긴다. 다음 조회에서 ai에 다시 물어 재시도한다(ai/server는 끝난 작업의 결과를 계속 보관한다).
5. 실패 횟수가 `app.job.result-save-max-attempts`(기본 5)에 닿으면 "작업 결과를 저장하지 못했습니다."로 `FAILED`를 기록한다.

- **`JobResultHandler`** (`job/service`): 대상 도메인(자료 준비·분석·예측)이 자기 작업 종류에 맞게 구현해 빈으로 등록한다. job은 대상 도메인을 직접 알지 않는다. 작업 종류마다 하나만 둔다(둘이면 기동 실패).
  처리기는 잠금 트랜잭션 안에서 불리므로 DB 저장만 하고 외부 호출을 하지 않는다. 저장하지 못하면 예외를 던진다.
- **처리기가 없는 작업 종류**: 경고 로그만 남기고 결과 없이 완료한다(이전 동작 그대로). 대상 도메인이 처리기를 붙이면 그때부터 저장된다. 자료 준비는 `DocumentPreparationResultHandler`(#111), 데이터 적재는 `DataSyncResultHandler`(#135)가 붙었고, 분석·예측은 아직 없다.

| ai 호출 결과 | 처리 |
|---|---|
| `AiJobNotFoundException` (ai에 없는 작업) | `FAILED`로 기록 |
| 그 외 오류 (네트워크 등) | 상태 유지, 다음 폴링에서 재시도 |

### 3.4 API

#### 📌 개요

작업(자료 준비, 분석, 예측)의 현재 상태를 조회한다. 아직 끝나지 않은 작업이면 ai 서비스의 최신 상태를 받아 저장한 뒤 돌려준다. 클라이언트는 `SUCCEEDED` 또는 `FAILED`가 될 때까지 이 API를 폴링한다.

#### 🔗 Endpoint

`GET /api/v1/jobs/{id}`

- 로그인한 사용자 누구나 조회할 수 있다(MVP). 인증은 user 이슈 이후 적용된다.

#### 📤 Request Body

없음

#### Request Param

| 속성 | 설명 | 타입 |
| --- | --- | --- |
| `id` | 작업 ID. 작업을 시작하는 API가 반환한 `jobId` (path) | number |

---

#### 📥 Response Body (200)

| 속성 | 설명 | 타입 |
| --- | --- | --- |
| `data.id` | 작업 ID | number |
| `data.jobType` | `DOCUMENT_PREPARATION` / `ANALYSIS` / `PREDICTION` / `DATA_SYNC` | string |
| `data.status` | `QUEUED` / `RUNNING` / `SUCCEEDED` / `FAILED` | string |
| `data.startedAt` | 시작 시각. 시작 전이면 `null` | string \| null |
| `data.finishedAt` | 종료 시각. 끝나지 않았으면 `null` | string \| null |
| `data.errorMessage` | 실패 사유. 실패가 아니면 `null` | string \| null |
| `error` | 성공이면 `null` | null |

```json
{
  "data": {
    "id": 42,
    "jobType": "ANALYSIS",
    "status": "RUNNING",
    "startedAt": "2026-11-16T09:30:00",
    "finishedAt": null,
    "errorMessage": null
  },
  "error": null
}
```

- 작업 결과 본문은 담지 않는다. 결과는 해당 도메인의 조회 API로 가져온다.
- 응답 형식은 코드의 `ApiResponse`(`data`, `error`)를 따른다. `status`, `message` 필드는 없다.

#### 📥 Response Body (에러)

```json
{
  "data": null,
  "error": { "code": "C002", "message": "ID 999번 작업을 찾을 수 없습니다." }
}
```

| HTTP | 코드 | 상황 |
|---|---|---|
| 404 | `C002` | 없는 작업 |

## 4. 왜 이렇게 했나

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 엔티티가 전이 규칙을 가진다 (`@Setter` 없음) | 규칙이 서비스 여러 곳에 흩어지면 한 곳만 빠뜨려도 잘못된 상태가 DB에 들어간다 | 서비스에서 상태를 직접 바꾸고 검사 |
| `QUEUED → FAILED` 허용 | ai 시작 요청이 실패하면 작업이 영원히 `QUEUED`로 남는다 | 이슈 원안(`QUEUED → RUNNING → 종료`만) |
| 같은 상태 반복은 예외가 아니라 무시 | 폴링은 같은 상태를 반복해 받는 것이 정상이다 | 모든 비허용 전이를 예외로 처리 |
| **조회할 때 갱신** | 사용자가 적고, 갱신 배치의 트리거 주체(Jenkins/Spring)가 아직 정해지지 않았다 | 주기 배치로 갱신 |
| ai 호출은 트랜잭션 밖 | 외부 호출 동안 DB 커넥션을 붙잡지 않는다 (`backend/CLAUDE.md` 규칙) | 한 트랜잭션 안에서 호출 |
| 저장 직전에 행을 잠그고(`SELECT ... FOR UPDATE`) 다시 읽어 `syncFrom` | 같은 작업의 동시 갱신을 한 줄로 세운다. 잠금 읽기는 가장 최근에 커밋된 값을 읽으므로, 뒤에 온 요청은 앞선 요청의 종료 상태를 보고 무시한다. 마이그레이션이 필요 없다. 잠금은 짧은 저장 트랜잭션에만 걸고 ai 호출은 잠금 밖이다 | 낙관적 락(`@Version`, 컬럼 추가 필요), 락 없이 재조회만 (코드 리뷰에서 경쟁 가능성 지적) |
| enum을 `AiJobStatus`(ai 쪽)와 `JobStatus`(DB)로 분리 | DB 값은 한번 쌓이면 바꾸기 어렵고, ai 계약은 초안이라 값이 늘 수 있다. 변환 한 곳만 고치면 된다 | 하나의 enum 공유 |
| "ai에 없는 작업"과 "일시 오류"를 다르게 처리 | 없는 작업은 기다려도 끝나지 않지만, 일시 오류는 다시 시도하면 된다 | 모든 오류를 `FAILED`로 |
| `Clock` 주입 | `now()`를 직접 찍으면 테스트가 불안정하다 | `LocalDateTime.now()` 직접 호출 |
| 결과 저장과 완료 확정을 한 트랜잭션으로 (#63) | 둘 중 하나만 되는 일이 없다. 행 잠금 뒤 종료 여부를 다시 보므로 처리기가 중복 저장을 따로 막지 않아도 된다 | 대상 도메인 저장을 먼저 커밋한 뒤 완료(처리기마다 멱등성 필요) |
| 처리기가 없으면 완료하고 경고 (#63) | 대상 도메인 구현 전까지 화면 흐름을 지금처럼 유지한다 | 진행 중으로 두기(화면이 계속 돎), 실패 처리(모든 작업이 실패로 보임) |
| 결과 저장 실패는 횟수 제한 (#63) | 계속 실패하는 작업이 영원히 끝나지 않는 것을 막는다. 기본 5회, 설정으로 조정 | 무기한 재시도 |
| 조회는 로그인한 사용자 전체에 허용 | `Job`에 소유자 컬럼이 없다. 응답에 결과 본문이 없어 MVP에서는 감수한다 | `Job`에 소유자 추가 |

### 4.1 결정 기록: 결과 저장 후에만 완료 확정 (#63)

출발점: 이전 `getJob`은 ai가 `SUCCEEDED`를 주면 `Job.status`부터 완료로 바꾸고 `result`는 아무도 저장하지 않았다.
한번 완료되면 ai를 다시 부르지 않으므로 결과를 되찾을 방법이 없었다(`ai-contract.md` 2.7).

#### D1. 결과 저장과 완료 확정을 한 트랜잭션으로 묶는다

| 후보 | 장점 | 단점 |
|---|---|---|
| **(a) 한 트랜잭션** (선택) | 저장과 완료 중 하나만 되는 일이 없다. 행을 잠근 뒤 종료 여부를 다시 보므로 처리기가 중복 저장을 따로 막지 않아도 된다 | 처리기는 DB 저장만 해야 한다(외부 호출을 하면 잠금이 길어진다). 처리기가 느리면 같은 작업의 다른 조회가 그만큼 기다린다 |
| (b) 대상 도메인 저장을 먼저 커밋한 뒤 완료 | 처리기가 파일 저장 같은 외부 작업을 할 수 있다 | 저장 커밋과 완료 커밋 사이에 실패하면 다음 조회에서 다시 저장한다. 처리기마다 멱등성(같은 결과를 두 번 받아도 한 번만 저장)을 직접 만들어야 한다 |

- **고른 이유**: 결과는 ai 응답으로 이미 메모리에 있어서, 처리기가 외부 호출을 할 일이 없다. (b)는 멱등성 부담을 앞으로 생길 모든 도메인(자료 준비·분석·예측)에 나눠 지운다.
- **확인한 근거**: 처리기가 DB에 한 줄을 쓴 뒤 실패하면 그 줄도 함께 되돌려지는지 테스트로 확인했다(`결과_저장이_실패하면_처리기가_쓴_내용도_함께_되돌린다`).

#### D2. 대상 도메인은 `JobResultHandler` 인터페이스로 연결한다

| 후보 | 판단 |
|---|---|
| **(a) job 패키지에 인터페이스를 두고, 대상 도메인이 구현해 빈으로 등록** (선택) | job은 대상 도메인을 모른다. 대상 도메인이 이미 job을 쓰므로(작업 생성) 의존 방향이 한쪽으로만 흐른다 |
| (b) `JobService`가 각 도메인 서비스를 직접 호출 | document → job → document처럼 순환 의존이 생긴다 |
| (c) 스프링 이벤트(`@EventListener`)로 결과 전달 | 같은 트랜잭션에서 부를 수는 있지만, 처리기가 없거나 둘인 경우를 기동 시점에 잡기 어렵고 실패가 호출한 쪽에 어떻게 전해지는지 코드만 봐서는 드러나지 않는다 |

- 작업 종류마다 처리기는 하나다. 둘이면 어느 쪽이 저장할지 모호하므로 기동을 멈춘다.

#### D3. 처리기가 없는 작업 종류는 결과 없이 완료하고 경고를 남긴다

| 후보 | 장점 | 단점 |
|---|---|---|
| **(a) 완료 + 경고 로그** (선택) | 대상 도메인이 처리기를 붙이기 전까지 화면 흐름이 지금과 같다 | 그동안 끝난 작업의 결과는 버려지고 되찾을 수 없다 |
| (b) 진행 중으로 둔다 | 결과는 ai에 남아 나중에 받을 수 있다 | 처리기가 생길 때까지 화면이 계속 돌고 폴링도 계속된다 |
| (c) 실패로 끝낸다 | 처리기 누락이 바로 드러난다 | 지금은 세 종류 모두 처리기가 없어 모든 작업이 실패로 보인다 |

- **고른 이유**: 지금은 실제로 작업을 시작하는 도메인이 아직 없어서 버려질 결과도 없다. 처리기는 첫 대상 도메인(#111 업로드)에서 붙는다. 코드에 TODO를 남겼다.

#### D4. 결과 저장 실패는 횟수를 세고, 5회에 닿으면 `FAILED`로 끝낸다

| 후보 | 판단 |
|---|---|
| (a) 무기한 재시도 | 마이그레이션이 필요 없다. 대신 계속 실패하는 작업(예: 결과 모양이 처리기와 맞지 않음)이 영원히 끝나지 않는다 |
| **(b) 횟수 제한** (선택) | 끝나지 않는 작업을 막는다. 횟수를 저장할 칼럼이 필요하다 |

- **횟수를 어디에 둘지**: 메모리 카운터는 재시작하면 사라지고 요청 사이에 공유되지 않는다. `job.result_save_failures` 칼럼(V10)에 둔다.
- **세는 방법**: 저장 트랜잭션은 실패하면 되돌려지므로, 실패 횟수는 새 트랜잭션에서 행을 잠근 뒤 올린다. 그 사이 다른 요청이 작업을 끝냈으면 세지 않는다.
- **5회를 고른 고민**: 횟수는 조회할 때만 오른다. 화면이 2초마다 폴링하면 5회는 약 10초 만에 찬다. DB가 잠깐 불안정해도 10초 만에 실패로 확정될 수 있다. 반대로 결과 모양이 맞지 않는 영구 실패라면 오래 기다릴 이유가 없다. MVP는 5회로 두고 `app.job.result-save-max-attempts`로 조정할 수 있게 했다. 갱신 배치가 생기면 배치 주기 기준으로 다시 정한다.
- **포기할 때 문구**: "작업 결과를 저장하지 못했습니다." 예외 내용은 결과 본문이 섞일 수 있어 사용자 문구와 로그 모두에 넣지 않는다(로그에는 예외 종류만).

#### D5. 동시 완료의 중복 저장은 기존 행 잠금으로 막는다

| 후보 | 판단 |
|---|---|
| **(a) 잠근 뒤 다시 읽어 이미 끝났으면 건너뛴다** (선택) | #35에서 쓰던 `findByIdForUpdate`를 그대로 쓴다. 마이그레이션도, 처리기 쪽 작업도 필요 없다 |
| (b) 처리기마다 멱등성 | D1의 (b)와 같은 부담 |
| (c) 대상 테이블에 유니크 제약 | 도메인마다 제약을 맞춰야 하고, 제약 위반을 실패로 세면 D4 횟수가 엉뚱하게 오른다 |

- **확인한 근거**: 두 요청이 같은 순간 `SUCCEEDED`를 받아도 처리기가 한 번만 불리는지 테스트로 확인했다(`같은_작업이_동시에_완료돼도_결과는_한_번만_저장된다`).

#### D6. "작업 없음"(404용 예외)은 저장 실패로 세지 않는다

- 잠금 조회 중 작업이 사라지면 `BusinessException`(404)이 난다. 이것까지 저장 실패로 세면 없는 작업의 횟수를 올리려다 다시 404가 난다. 그래서 `BusinessException`은 그대로 던지고, 그 밖의 예외만 저장 실패로 센다.

## 5. 미정

| 항목 | 현재 처리 | 정해지는 곳 |
|---|---|---|
| 조회 권한의 최종 정책 (본인 작업만?) | 로그인한 사용자 전체 | 대상 도메인 구현 시 |
| 갱신 배치 도입 여부와 트리거 주체 | 조회할 때만 갱신 | datasync 스케줄러 결정과 함께 |
| 오래된 `QUEUED`/`RUNNING` 작업의 타임아웃 정책 | 없음 | 정리 배치 결정 시 |
| ai 호출 계약 (`PythonAiClient`는 가칭 초안) | Stub 기준 | 실제 ai 서비스 연동 시 |
| 시간대 | 시스템 기본값 | 시간대 정책 결정 시 (api-spec 미정 항목) |
| 폴링 간격 권장값 | 정해지지 않음 | api-spec |
| 에러 코드 접두사(`J`) | 임시 | api-spec 확정 시 |
| 작업 취소, 재시도 | 지원하지 않음 | 요구가 생길 때 |

## 6. 알려진 문제와 한계

| 문제 | 영향 | 비고 |
|---|---|---|
| GET이 쓰기를 한다 | 조회가 부수 효과를 가진다. 조회 안 하는 작업은 갱신되지 않는다 | MVP 선택 |
| 진행 중인 작업은 폴링마다 ai를 호출한다 | 사용자와 폴링 빈도가 늘면 ai 호출이 비례해 늘고, 같은 작업의 동시 폴링이 각자 호출한다 | 종료되면 호출이 멈춘다 |
| 같은 작업을 동시에 폴링하면 저장 단계가 줄을 선다 | 행 잠금 때문에 뒤 요청이 앞 요청의 짧은 트랜잭션이 끝날 때까지 기다린다. 잠금 시간이 짧아 지금은 문제 없다 | 대기가 길어지면 `@Version` 방식을 검토 |
| `markStarted`, `markFailed`는 잠금 조회를 쓰지 않는다 | 작업을 만든 쪽이 한 번씩 호출하는 흐름이라 경쟁 가능성이 낮다고 봤다. `getJob` 갱신과 동시에 일어나면 어긋날 수 있다 | 문제가 보이면 두 메서드도 잠금 조회로 바꾼다 |
| 오래된 `QUEUED`/`RUNNING` | 생성 직후 서버가 죽거나, 일시 오류가 계속되면 상태가 영원히 안 끝난다 | 타임아웃 정리가 필요 |
| ai의 `errorMessage`를 그대로 저장하고 응답한다 | 내부 사정이나 문서 내용이 담기면 클라이언트에 노출된다 | 실제 ai 연동 전에 정제 방식 결정 필요 |
| "없는 작업" 판단이 ai 구현체에 의존한다 | 실제 구현체가 일시 장애도 이 예외로 던지면 멀쩡한 작업을 `FAILED`로 만든다 | 구현체는 404일 때만 던져야 한다 |
| 순차 ID와 소유자 미검사 | 남의 작업 상태를 추측해 볼 수 있다 | 인증·소유자 제한 때 해결 |
| 결과 저장 실패 횟수는 조회할 때만 센다 | 아무도 조회하지 않으면 한도에 닿지 않고 진행 중으로 남는다. 횟수는 조회 빈도에 따라 빨리 찰 수 있다(폴링 2초면 5회는 약 10초) | 갱신 배치가 생기면 배치 주기 기준이 된다 |
| 처리기가 없는 작업 종류는 결과를 버린다 | 대상 도메인이 처리기를 붙이기 전에 끝난 작업의 결과는 되찾을 수 없다 | 대상 도메인 이슈(#111 등)에서 처리기를 붙인다 |
| 테스트가 가짜 ai 대역 기준이다 | 실제 Stub·HTTP 구현체와의 통합, 대상 도메인과의 흐름은 검증하지 않았다 | 연동 시 추가 |

## 7. 확장

| 하려는 것 | 방법 |
|---|---|
| 갱신 배치 | 스케줄러가 미종료 작업을 훑어 `getJob`의 갱신 로직(3~4단계)을 재사용한다. 이후 `getJob`은 순수 조회로 되돌릴 수 있다 |
| 본인 작업만 조회 | `Job`에 소유자 컬럼을 추가(새 마이그레이션)하거나, 대상 도메인이 `jobId`로 소유자를 조회해 검사한다 |
| 동시 갱신 방어 강화 | 잠금 대기가 문제되면 `job.version` 컬럼과 `@Version`(낙관적 락)으로 전환한다 (새 마이그레이션) |
| 타임아웃 정리 | `startedAt`/`createdAt` 기준 N분이 지난 미종료 작업을 `FAILED`로 기록하는 배치 |
| 작업 종류 추가 | `JobType` 값 추가. 컬럼이 VARCHAR라 마이그레이션은 필요 없고, 대상 도메인이 `jobId`로 연결한다 |
| 취소 | `CANCELED` 상태 추가: `JobStatus` 전이 표, `AiJobStatus` 변환, 종료 상태 판정을 함께 고친다 |
| 실제 ai 구현체 | `PythonAiClientHttp`(#114). 404만 `AiJobNotFoundException`으로 변환한다 |
| 대상 도메인 결과 저장 | 대상 도메인 서비스가 `JobResultHandler`를 구현해 빈으로 등록한다. DB 저장만 하고 실패하면 예외를 던진다 |
| 폴링 부하 완화 | 응답에 권장 폴링 간격을 알려 주거나, 짧은 시간 내 같은 작업의 ai 호출을 합친다 |
