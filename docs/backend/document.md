# document 도메인 — 사용자 문서 업로드

> 작성자 : 윤혜정

> 사용자가 캔버스에서 예산서·근거자료를 올리고, 파싱 결과를 문서 카드로 받는 부분이다. 이슈 #111 기준.
> 코드가 바뀌면 이 문서도 함께 고친다.

## 1. 역할

- 캔버스에 파일 하나를 올리면 원본을 저장하고, 문서·문서 버전·자료 준비 작업을 만들고, ai 서비스에 파싱을 요청한다.
- 작업이 끝나면 ai가 돌려준 결과(요약·수치·태그)를 저장하고, 문서 조회로 카드 데이터를 돌려준다.
- 올린 파일은 그 캔버스에 속한다. 올리기는 편집 권한자(소유자·편집), 보기는 캔버스 권한자 모두.
- 업로드 원본만 다룬다. 공시 같은 공용 문서 원본은 ai 쪽이 보관한다(`ai-contract.md` 2.11).
- 사용자 업로드는 ChromaDB에 적재하지 않는다. 파싱해 결과만 돌려받는다.

## 2. 구성

| 클래스 | 역할 |
|---|---|
| `DocumentController` | `POST /api/v1/documents/uploads`, `GET /api/v1/documents/{id}` |
| `DocumentService` | 업로드 순서(3.1)와 문서 조회 |
| `DocumentPreparationResultHandler` | `JobResultHandler`(#63) 구현. 자료 준비 작업이 끝나면 결과를 저장 |
| `DocumentUploadProperties` | 허용 확장자(`app.document.upload.allowed-extensions`) |
| `Document`, `DocumentVersion`, `DocumentPreparationResult` | 엔티티. 스키마는 `V4`, `V11` |

## 3. 구현

### 3.1 업로드 순서

`job.md` 3.3 "다른 도메인이 작업을 시작하는 순서"를 따른다.

1. 입력 확인: 필수 값(`canvasId`, `company`)은 `C001`. 빈 파일·확장자는 `D001` `FORMAT_MISMATCH`, 대상 회사가 아니면 `D001` `COMPANY_MISMATCH`.
   크기 상한은 서블릿이 먼저 막는다(50MB). 거절은 모두 파일을 저장하기 전에 한다.
2. 캔버스가 있고(삭제 안 됨) 편집 권한(소유자·편집)이 있는지 확인. 보기는 `K002`, 권한 없음은 `K001`.
3. 원본을 `FileStorage`에 저장 (트랜잭션 밖).
4. 한 트랜잭션: `Job`(`DOCUMENT_PREPARATION`, QUEUED) + `Document` + `DocumentVersion`(버전 1, `canvas_id`, `uploaded_by`).
   실패하면 3에서 올린 파일을 지운다.
5. ai 자료 준비 시작 (트랜잭션 밖). 성공하면 `markStarted`, 실패하면 `markFailed`(자동 재시도 없음).
6. `202` + `{ jobId, documentIds: [id] }`. ai 시작이 실패해도 `202`이며, 화면은 폴링에서 `FAILED`와 사유를 본다.

### 3.2 결과 저장과 조회

- `GET /jobs/{id}` 폴링 중 ai가 `SUCCEEDED`를 주면 `JobService`가 `DocumentPreparationResultHandler`를 부른다. 처리기는 작업에 연결된
  문서 버전을 찾아 결과 JSON을 `document_preparation_result`에 저장한다. 저장과 완료 확정은 한 트랜잭션이다(`job.md` 3.3).
- `GET /documents/{id}`는 최신 버전과 결과를 읽어 프론트 명세의 `Doc`으로 돌려준다. 결과의 `summary`(문자열), `figures`·`tags`(목록)만 꺼내고,
  모양이 다르면 빈 값으로 둔다. 준비가 끝나기 전에도 조회되며 그때는 요약·수치·태그가 비어 있다.

### 3.3 서버가 정하는 값

| 칼럼 | 값 |
|---|---|
| `document.document_type` | `INTERNAL` (화면 `kind`는 `internal`) |
| `document.title` | 파일명에서 확장자를 뺀 것 (255자까지) |
| `document_version.source` | `사내 업로드` (화면 `publisher`) |
| `document_version.published_date` | 요청의 `publishedDate`, 없으면 올린 날 |
| `document_version.version_no` | 1 (업로드마다 새 문서) |
| `document.company` | 사용자가 고른 회사를 대상 회사 목록의 표기로(예: `lgu+` → `LGU+`) |

## 4. 결정 기록 (#111)

### U1. 한 요청에 파일 하나, 파일마다 작업 하나

| 후보 | 장점 | 단점 |
|---|---|---|
| **(a) 요청당 파일 하나** (선택) | 응답 `{ jobId, documentIds }` 모양이 프론트 명세 그대로다. DB의 "문서 버전 하나 = 작업 하나"(`uk_document_version_job`)도 그대로다 | 화면이 파일마다 요청한다(데모 화면도 이미 파일마다 돈다) |
| (b) 한 요청, 파일마다 작업 | 요청 한 번에 끝난다 | 응답을 목록으로 바꿔야 해서 프론트 명세와 화면을 고쳐야 한다 |
| (c) 작업 하나에 여러 파일 | 프론트 명세 그대로 | DB 제약을 바꿔야 하고, 파일 하나만 실패해도 작업 전체가 실패로 보인다 |

- **고민한 점(여러 파일을 "합칠" 수 있나)**: 여러 문서를 함께 쓰는 곳은 업로드가 아니라 분석이다. 분석이 `AnalysisRunDocument`로 문서 버전 여러 개를
  묶는다(예산서 1개 + 근거자료 여러 개). 그래서 파싱은 파일마다 따로 해도 된다. 파일마다 따로 하면 하나가 깨져도 나머지는 정상으로 끝나고,
  화면이 파일별 진행 상태를 보여 줄 수 있다.
- `documentIds`는 하나뿐이지만 프론트 명세 모양을 지키려고 목록으로 둔다.

### U2. 회사·발행일은 요청으로 받고, 나머지는 서버가 정한다 (회사는 사용자가 고른다)

| 후보 | 판단 |
|---|---|
| **(a) 회사(필수)·발행일(선택, 없으면 올린 날)은 요청, 제목·출처·종류는 서버** (선택) | 데모 화면(현재 회사, 파일명, 올린 날)과 같다. 입력란을 늘리지 않으면서 기준 시점 문제를 피할 길을 남긴다 |
| (b) 전부 서버 | 과거 자료를 올리면 기준 시점 필터에서 빠진다 |
| (c) 전부 요청 | 가장 정확하지만 화면 입력이 늘어난다 |

- **회사는 사용자가 고른다(확정)**: 화면 데모는 파일 이름·본문에서 회사를 추정했지만, 사용자가 목록에서 고르는 방식으로 정했다(PR #122 리뷰).
  backend는 파일 내용으로 회사를 추정하지 않고 고른 값을 검사만 한다(U10).
- **발행일이 중요한 이유**: 예측·평가는 기준 시점(`asOfDate`) 이전에 발행된 자료만 쓴다(루트 `CLAUDE.md` 4번). 발행일을 늘 올린 날로 두면,
  지난 분기 기준으로 분석할 때 방금 올린 지난 분기 예산서가 빠진다. 그래서 요청으로 받을 수 있게 했다.

### U3. 크기 상한은 50MB

| 후보 | 판단 |
|---|---|
| **50MB** (선택) | 큰 예산서·IR PDF도 대부분 들어간다. 업로드는 임시 파일을 거쳐(파일 저장소 D5) 메모리에 다 올리지 않는다 |
| 20MB / 10MB | 파싱 부담은 작지만 스캔본 PDF가 넘길 수 있다 |

- `spring.servlet.multipart.max-file-size: 50MB`, `max-request-size: 51MB`(다른 필드 여유).
- 넘으면 `413` + `C001` "파일이 너무 큽니다 (최대 50MB)." Tomcat은 예외에 상한을 담지 않아(-1) 설정 값을 문구에 쓴다(로컬 기동으로 확인).
- **배포 주의**: 배포 Ingress(nginx)의 기본 body 크기 제한은 1MB라, infra 쪽에 `proxy-body-size` 설정이 필요하다. 없으면 1MB를 넘는 파일이
  backend에 닿기 전에 Ingress에서 `413`으로 막힌다.

### U4. 허용 형식은 ai 파서가 읽는 형식으로 임시 제한한다

| 후보 | 판단 |
|---|---|
| **(a) 파서 지원 형식만** (선택) | 읽지 못할 파일을 S3에 쌓고 작업을 돌린 뒤 실패시키는 대신, 저장 전에 `400`으로 바로 알린다 |
| (b) 제한 없음 | 무엇이든 받고 파싱 단계에서 실패한다. 원본은 S3에 남는다 |

- 목록: `pdf, xlsx, xlsm, csv, pptx, html, htm, xml, txt, md, json` (`pipelines/parsers/loaders.py`의 `_EXT`와 같다). 설정으로 바꿀 수 있다.
- 허용 형식은 루트 `CLAUDE.md` 7장의 "정해지지 않은 것"이다. 이 목록은 임시이며 정책이 정해지면 바꾼다.
- 목록이 비면 아무것도 받지 않는다(설정 누락을 "모두 허용"으로 해석하지 않는다).

### U5. 파싱 결과는 별도 테이블에 JSON 그대로 둔다

| 후보 | 판단 |
|---|---|
| (a) `document_version`에 결과 칼럼 | 결과는 작업이 끝난 뒤 생긴다. 만든 뒤 바뀌지 않는 문서 버전(불변 규칙)을 나중에 고쳐야 한다 |
| **(b) 별도 테이블, 결과 JSON 그대로** (선택) | 문서 버전은 그대로 불변이다. ai 결과 형식이 확정 전(#109)이라 형식이 바뀌어도 마이그레이션 없이 따라간다 |
| (c) 별도 테이블, `summary`·`figures`·`tags` 칼럼 | 모양이 분명하지만 형식이 정해지면 마이그레이션이 더 필요할 수 있다 |

- `document_preparation_result(document_version_id UNIQUE, result JSONB)`. 문서 버전마다 하나.
- 조회할 때 `summary`·`figures`·`tags`를 꺼내고, 모양이 다르면 빈 값으로 둔다(500을 내지 않는다).
- 결과 저장 시점은 #63의 "결과 저장 후에만 완료 확정"을 그대로 쓴다. 이 도메인은 처리기만 구현했다.

### U6. 캔버스 연결은 `document_version.canvas_id`

| 후보 | 판단 |
|---|---|
| **(a) `document_version.canvas_id`** (선택) | 버전을 만들 때 한 번 넣고 바꾸지 않아 불변 규칙과 맞는다. `uploaded_by`와 같은 자리라 권한 확인이 단순하다. 공용 문서는 비어 있다 |
| (b) 연결 테이블 `canvas_document` | 한 문서를 여러 캔버스에 걸 수 있지만, "올린 파일은 그 캔버스에 속한다"는 결정보다 넓다 |

- 업로드마다 새 문서·버전 1을 만든다. 같은 파일을 다른 캔버스에 쓰려면 다시 올린다.

### U7. ai 시작이 실패해도 `202`로 답한다

- 문서·버전·작업은 이미 커밋됐다. 시작 실패는 작업을 `FAILED`로 기록하고 `202`로 답한다. 화면은 다른 실패와 같은 길(폴링)로 사유를 본다.
- 사유: `AiCallFailedException`이면 그 문구("ai 서비스가 아직 지원하지 않는 작업입니다." 등)를, 예상하지 못한 오류면 내부 사정을 감추고
  "ai 서비스에 작업을 시작하지 못했습니다."를 남긴다.
- 버린 대안: 시작 실패를 `5xx`로 답하기. 이미 만든 문서와 작업이 남는데 화면은 실패로만 알게 되어, 남은 문서를 어떻게 볼지가 애매해진다.

### U8. 저장 실패 시 파일을 지운다

- 원본 저장(외부 I/O)은 트랜잭션 밖에서 먼저 한다(`backend/CLAUDE.md` "외부 호출을 트랜잭션 안에서 길게 잡지 않는다").
- 그래서 DB 저장이 실패하면 저장소에 고아 파일이 남는다. 실패하면 그 키를 지운다. 지우기마저 실패하면 오류 로그만 남긴다.
- 확인한 근거: 파일 저장 직후 `document` 테이블에 새 행을 막는 제약을 걸어 저장을 실패시키고, 파일이 지워지고 작업도 함께 되돌려지는지 테스트로 확인했다.

### U9. 권한 확인은 캔버스 서비스에 맡긴다

- `CanvasAccessService.loadActive` + `requireEdit`/`requireView`를 쓴다(기능 간 호출은 Service로만, `backend/CLAUDE.md` 3장).
- 삭제된 캔버스의 업로드 문서는 `404`로 보인다(캔버스를 찾을 수 없음).

### U10. 대상 회사는 설정 목록으로 두고, 지금은 4곳

- 결정: 지금 대상은 `SKT`, `SKB`, `KT`, `LGU+` 네 곳이다. 늘어날 수 있으므로 코드에 박지 않고 `app.document.upload.companies`에 둔다.
  회사를 늘릴 때는 설정만 바꾸면 되고, 화면의 선택 목록도 같은 값을 써야 한다.
- 비교한 안: enum으로 고정(늘릴 때 코드·배포가 필요), 검사 안 함(아무 회사나 들어와 3사 비교·분석 대상과 어긋남).
- 대소문자와 앞뒤 공백은 무시하고, 저장은 목록의 표기 그대로 한다(`lgu+` → `LGU+`). 같은 회사가 여러 표기로 쌓이지 않게 하려는 것이다.
- 참고: 프로젝트 개요는 "통신 3사"인데 SKB(SK브로드밴드)가 포함됐다. 화면(PR #122)과 같은 목록이다.

### U11. 업로드 거절은 `D001` + `data.reason`으로 알린다

| 후보 | 응답 예 | 판단 |
|---|---|---|
| **(a) 새 문서 코드 + 이유는 `data`** (선택) | `{ "data": { "reason": "FORMAT_MISMATCH" }, "error": { "code": "D001", ... } }` | 기존 코드 규약(영역 글자 + 번호)을 지키면서 화면이 `reason`으로 나눈다. `K003`이 `data`에 현재 글을 담는 것과 같은 방식 |
| (b) 코드 자체를 이름으로 | `{ "error": { "code": "FORMAT_MISMATCH" } }` | 화면 코드를 그대로 쓸 수 있지만 이 둘만 코드 규약에서 벗어난다 |
| (c) `C001` + 이유는 `data` | `{ "data": { "reason": ... }, "error": { "code": "C001" } }` | 새 코드가 없지만, 다른 입력 오류와 코드만으로는 구분되지 않는다 |

- 형식 불일치(`FORMAT_MISMATCH`): 허용하지 않는 확장자, 확장자 없음, 빈 파일. 화면 데모가 빈 파일을 형식 불일치로 본 것과 맞췄다.
- 회사 불일치(`COMPANY_MISMATCH`): 대상 회사 목록에 없는 회사.
- 필수 값 누락(`file`, `canvasId`, `company` 없음)은 화면 버그에 가까워 `C001`로 둔다. 크기 초과는 `413` `C001`(U3) 그대로다.
- 화면 PR #122의 `validate.ts`가 같은 이름(`FORMAT_MISMATCH`, `COMPANY_MISMATCH`)을 쓴다. 화면은 `error.data.reason`을 읽으면 된다.

## 5. 알려진 한계

| 문제 | 영향 | 비고 |
|---|---|---|
| 배포 Ingress 크기 제한(기본 1MB) | 1MB를 넘는 파일이 Ingress에서 막힌다 | infra에 `proxy-body-size` 요청 필요 |
| 배포 ai/server가 가짜 모드 | 지금 배포에서 올리면 가짜 결과가 저장된다 | #109에서 실제 모드로 바꾼 뒤 배포해야 한다 |
| 업로드 원본·결과를 지우는 길이 없다 | S3와 DB에 계속 쌓인다 | 문서 보관·삭제 정책(루트 `CLAUDE.md` 7장) |
| 공용 문서 조회는 다루지 않는다 | `GET /documents/{id}`는 지금 업로드 문서만 의미가 있다 | 공용 문서 검색·조회는 MCP 쪽 |
| 결과 형식이 확정 전 | 형식이 다르면 카드가 비어 보인다 | #109에서 ai와 확정 |
