> 작성자 : 윤혜정 (이슈 #36)

> 화면이 부르는 API의 **경로와 필드는 `docs/frontend/api-spec.md`**(프론트 API 명세)를 기준으로 한다.

### 1.2 응답 형식 (`ApiResponse`) [현재]

성공이면 `error`가 `null`, 실패면 `data`가 `null`이다. 최상위에 `status`, `message` 필드는 없다.

```json
{ "data": { "id": 42 }, "error": null }
```

```json
{ "data": null, "error": { "code": "C002", "message": "ID 42번 작업을 찾을 수 없습니다." } }
```

- 화면은 `error.code`로 분기한다. `error.message`는 표시용이며 같은 코드라도 문구가 구체적으로 바뀔 수 있다.
- 에러 응답에 화면이 다시 그릴 데이터가 필요하면 `data`에 담는다(예: 글 충돌 시 현재 글, 5.3).

### 1.3 목록 (`PageResponse`) [현재 응답 형식, 요청 파라미터는 제안]

페이지가 필요한 목록은 `data`에 `{ content, page, size, totalElements, totalPages, hasNext }`를 담는다. `page`는 0부터 시작한다.
요청 파라미터는 `?page=0&size=20`(기본 20, 최대 100)을 제안한다. 활동 로그처럼 개수가 정해진 목록은 배열을 그대로 담는다.

## 3. 인증·사용자 [제안] (#34)

### 3.1 사용자 필드 (`User`)

| 필드 | 설명 | 타입 |
|---|---|---|
| `id` | 사용자 ID. 숫자 PK. API 경로·요청에서 사람을 가리킬 때는 이 값을 쓴다 | number |
| `employeeNo` | 사번. 로그인과 검색·표시에만 쓴다 | string |
| `name` | 이름 | string |
| `dept` | 부서. 표시용이며 권한에 쓰지 않는다 | string |
| `job` | 직무 (예: 재무기획, 부서장). 표시용 | string |
| `role` | 서비스 전체 역할 `ADMIN` / `USER`. 공용 문서 수집·삭제는 `ADMIN`만 | string |

- 사번을 ID로 쓰지 않는 이유: 사번은 사람이 읽는 업무 값이라 바뀌거나 형식이 달라질 수 있고, 다른 테이블이 참조하는 키는 바뀌지 않아야 한다.
- 비밀번호 해시는 어떤 응답에도 담지 않는다.
- users 테이블(V2)에 `employee_no`(고유), `dept`, `job` 컬럼이 필요하다. `login_id`는 사번으로 대체한다. 새 마이그레이션으로 처리한다(#34).

### 3.2 규칙

- 로그인은 사번 + 비밀번호(`POST /api/v1/auth/login`). 응답은 `{ accessToken, tokenType: "Bearer", expiresIn, user }`.
- 로그아웃은 서버 호출 없이 토큰을 버린다.
- 사용자 검색(`GET /api/v1/users?q=`)은 사번·이름·부서 일부로 찾는다. 응답에 `role`은 담지 않는다.

| 상황 | HTTP | 코드 |
|---|---|---|
| 사번 없음, 비밀번호 불일치 | 401 | `A001` |
| `Authorization` 헤더 없음, `Bearer` 형식 아님, 서명 위조 | 401 | `A002` |
| 토큰 만료 | 401 | `A003` |
| 관리자 전용 기능을 `USER`가 호출 | 403 | `A004` |

## 4. 캔버스 권한 [제안] (#82)

캔버스마다 **소유자**(만든 사람) 한 명이 있고, 소유자가 다른 사용자를 **편집** 또는 **보기**로 초대한다. 부서는 권한에 쓰지 않는다.
일반 액세스(회사 전체 공개)는 두지 않는다. 캔버스는 소유자와 직접 초대받은 사람만 볼 수 있다.

| 기능 | 소유자 | 편집 | 보기 | 권한 없음 |
|---|---|---|---|---|
| 캔버스 열기, 활동 로그, 비교·근거·프롬프트 조회, 공유 명단 보기 | ○ | ○ | ○ | `K001` |
| 카드·연결 조작 (`events`) | ○ | ○ | `K002` | `K001` |
| 초안·질문 생성, 평가 | ○ | ○ | `K002` | `K001` |
| 초안·질문·평가 결과 보기 (다른 사람이 만든 것 포함) | ○ | ○ | ○ | `K001` |
| 실시간 구독, 커서 공유 | ○ | ○ | ○ | `K001` |
| 이름 변경 | ○ | ○ | `K002` | `K001` |
| 삭제 | ○ | `K002` | `K002` | `K001` |
| **공유 설정 변경 (초대·권한 변경·내보내기)** | ○ | `K002` | `K002` | `K001` |

- 초대는 수락 단계 없이 바로 반영된다.
- 소유자는 한 명이며 권한을 바꾸거나 내보낼 수 없다. 소유권 넘기기는 MVP 범위 밖이다.
- 권한은 HTTP 요청과 실시간 구독 모두에서 서버가 확인한다. 공유가 풀린 사람은 다음 요청부터 `K001`을 받고, 열어 둔 실시간 구독도 끊긴다.
- 공유 설정 변경과 그 결과는 활동 로그에 남는다.
- 캔버스 목록은 내가 소유했거나 초대받은 캔버스다. 각 항목에 내 권한(`owner` / `edit` / `view`)을 담는다.
- 삭제는 목록에서 숨기는 방식(삭제 표시)을 제안한다. 그 캔버스로 만든 초안·질문·평가 결과는 남는다.
- **결과물 조회 범위 (결정)**: 캔버스에서 만든 초안·질문·평가는 만든 사람만이 아니라 **그 캔버스에 권한이 있는 사람 모두**가 본다.
  결과물에는 만든 사람(`createdBy`)을 남긴다. 공유가 풀리면 그 캔버스의 결과물도 볼 수 없다.
  루트 `CLAUDE.md` 1번 "분석·예측 결과는 요청한 본인만 조회한다"를 이 규칙으로 바꿔야 한다(#79).

## 5. 캔버스 실시간 동시 편집 [제안] (#82, #83, #84)

여러 사람이 같은 캔버스를 동시에 고쳐도 변경이 사라지지 않고, 다른 사람의 변경과 커서가 바로 보이게 하는 규칙이다.
실시간 동시 편집과 커서 공유는 MVP에 포함한다(결정). backend와 화면의 서버 연동 계층에 함께 적용한다.

| 하는 일 | 경로 | 이유 |
|---|---|---|
| 편집 저장 | HTTP `POST /canvases/{id}/events` (5.2) | 트랜잭션·`requestId` 재전송·글 충돌(409)을 요청 하나에서 처리하고 응답으로 성공·실패를 바로 안다 |
| 다른 사람의 변경 받기 | WebSocket 구독 (5.5) | 커밋된 변경을 바로 받는다 |
| 커서·접속자 | WebSocket 보내기·구독 (5.6) | 저장하지 않는 짧은 메시지를 자주 주고받는다 |

### 5.1 ID

- 카드·연결 ID는 화면이 **UUID**로 만든다. 여러 사람이 동시에 만들어도 겹치지 않는다(데모의 `c{n}`, `l{n}` 순번은 쓰지 않는다).
- 캔버스 ID는 서버가 발급하는 숫자다.

### 5.2 이벤트 묶음 (`POST /api/v1/canvases/{id}/events`)

| 요청 필드 | 설명 |
|---|---|
| `requestId` | 묶음마다 화면이 만드는 UUID. 같은 묶음을 다시 보낼 때는 **같은 값** |
| `events` | 이벤트 목록 (종류는 프론트 명세). 작성자는 토큰의 사용자이며 요청 값을 쓰지 않는다 |

| 응답 필드 | 설명 |
|---|---|
| `lastSeq` | 반영 후 마지막 이벤트 번호 |
| `firstChangedLayer` | 처음 바뀐 컨텍스트 층 |
| `textVersions` | 이번 묶음으로 바뀐 글의 새 버전. 키는 카드·연결 ID, 값은 `{ text?, prompt? }` (5.3) |

- 한 묶음은 한 트랜잭션이다. 카드 상태 변경과 이벤트 로그를 같이 저장하고, 하나라도 실패하면 묶음 전체를 반영하지 않는다.
- 이벤트 번호(`seq`)는 캔버스 단위로 1씩 늘어난다. 같은 캔버스의 묶음은 순서대로 저장한다(캔버스 행 잠금).
- 같은 `requestId`가 다시 오면 저장하지 않고 처음 응답을 그대로 돌려준다(전송 실패 후 재전송 대비).

### 5.3 같은 카드를 동시에 고칠 때

- 위치(`move_card`)와 글은 다른 필드라 서로 덮어쓰지 않는다. 한 사람이 카드를 옮기는 동안 다른 사람이 같은 카드의 프롬프트를 고쳐도 둘 다 남는다.
- 위치는 나중에 저장된 값이 이긴다.
- 여러 사람이 고칠 수 있는 글은 세 가지이고, 글마다 버전을 따로 둔다. 바뀔 때마다 1씩 오른다.

  | 글 | 이벤트 | 버전 필드 (캔버스 열기 응답) |
  |---|---|---|
  | 프롬프트 카드 본문 | `edit_prompt` (`cardId`, `text`, `baseVersion`) | 카드의 `textVersion` |
  | 카드 프롬프트 (프롬프트 카드 외 모든 카드) | `set_card_prompt` (`cardId`, `text`, `baseVersion`) | 카드의 `promptVersion` |
  | 선 프롬프트 | `set_link_prompt` (`linkId`, `text`, `baseVersion`) | 연결의 `promptVersion` |

- 세 이벤트는 고치기 시작한 시점의 버전을 `baseVersion`으로 보낸다. 현재 버전과 다르면 묶음 전체를 `409 K003`으로 거절하고,
  `data`에 현재 글 `{ targetId, field, text, version }`(`field`는 `text` 또는 `prompt`)을 담는다.
  화면은 최신 글을 보여 주고 다시 고치게 하며, 나머지 이벤트는 새 `requestId`로 다시 보낸다.
- 새로 만든 프롬프트 카드(`add_prompt`)의 본문 버전은 1이다. 성공 응답의 `textVersions`로 새 버전을 알려 준다.
- 시각화 카드도 저장한다: `add_chart`(`cardId`, `compareId`, `x`, `y`). 새로고침 뒤에도 남게 하기 위해서다.
- 결정 이유(버전 비교를 고른 이유, 다른 선택지)는 `docs/backend/canvas.md` D3.

### 5.4 다른 사람의 변경 받기와 복원

- 커밋된 변경만 다른 사람에게 보낸다. 트랜잭션이 커밋된 뒤에 보내므로(`@TransactionalEventListener(AFTER_COMMIT)`) 롤백된 묶음은 보내지 않는다.
- 받는 쪽은 `seq`가 이어지는지 확인하고, 빠진 번호가 있거나 재접속하면 캔버스 전체를 다시 조회한다(`GET /api/v1/canvases/{id}`의 `lastSeq` 기준).
- 캔버스를 열 때 일부 카드를 복원하지 못해도(가리키는 표·문서가 사라짐) `200`으로 나머지를 돌려주고 `warnings[]`에 이유를 담는다. 조회 실패(409)로 처리하지 않는다.
- 상태는 서버에 저장되므로 새로고침·재접속·서버 재시작 뒤에도 같은 상태로 열린다.

### 5.5 실시간 연결 (WebSocket + STOMP)

**연결**

| 항목 | 규칙 |
|---|---|
| 주소 | `wss://{호스트}/api/v1/ws` (Ingress의 `/api` 경로로 backend에 간다) |
| 프로토콜 | STOMP 1.2 over WebSocket. SockJS 대체 경로는 쓰지 않는다 |
| 인증 | STOMP `CONNECT` 프레임의 `Authorization: Bearer {accessToken}` 헤더. 토큰을 주소(쿼리)에 넣지 않는다 |
| 하트비트 | 서버·화면 모두 10초. Ingress(nginx)의 기본 60초 무응답 끊김보다 짧게 둔다 |
| 끊김 | 화면이 자동으로 다시 연결하고, 다시 구독한 뒤 캔버스를 다시 조회한다 |

**구독과 보내기**

| 방향 | 목적지 | 내용 | 권한 |
|---|---|---|---|
| 구독 | `/topic/canvases/{id}/events` | 커밋된 이벤트 묶음 | 캔버스 권한자 |
| 구독 | `/topic/canvases/{id}/cursors` | 다른 사람의 커서 (5.6) | 캔버스 권한자 |
| 구독 | `/topic/canvases/{id}/presence` | 접속자 들어옴·나감 (5.6) | 캔버스 권한자 |
| 구독 | `/app/canvases/{id}/presence` | 지금 접속자 목록을 한 번만 받음 (5.6) | 캔버스 권한자 |
| 구독 | `/user/queue/canvases` | 나에게만 오는 알림: 권한 바뀜·회수, 캔버스 삭제 | 본인 |
| 보내기 | `/app/canvases/{id}/cursor` | 내 커서 위치 (5.6) | 캔버스 권한자 |

- 구독(`SUBSCRIBE`)과 보내기(`SEND`) 때마다 서버가 캔버스 권한을 확인한다. 권한이 없으면 STOMP `ERROR`(`K001`)로 거절한다.
  STOMP 규약상 `ERROR`를 보낸 연결은 닫히므로, 화면은 다시 연결해야 한다. 권한이 있는 캔버스만 구독하면 이 일은 생기지 않는다.
- 커서 보내기는 그 캔버스를 (권한 확인을 거쳐) 구독 중인 연결에서만 받는다.
- 편집 저장은 WebSocket으로 받지 않는다. 항상 HTTP(5.2)로 보낸다.

**이벤트 메시지** (`/topic/canvases/{id}/events`)

```json
{
  "firstSeq": 41,
  "lastSeq": 43,
  "requestId": "6f1c2a1e-6c1e-4d0f-9a43-7d3f8a0b9c21",
  "author": { "id": 2, "name": "박망" },
  "events": [ { "type": "move_card", "cardId": "0d9f…", "x": 140, "y": 96 } ],
  "textVersions": { "7a21…": { "prompt": 4 } }
}
```

- 받는 쪽은 `firstSeq`가 자신이 가진 마지막 `seq` + 1인지 확인한다. 아니면 캔버스를 다시 조회한다.
- 보낸 사람도 같은 메시지를 받는다. 자기 `requestId`면 이미 화면에 반영했으므로 `seq`만 갱신한다.
- 처음 열 때 순서: 구독 → 캔버스 조회(`lastSeq`) → 구독으로 받은 메시지 중 `lastSeq`보다 큰 것만 적용. 조회와 구독 사이에 들어온 변경을 놓치지 않기 위해서다.

**권한 회수**

- 공유에서 빠지거나 캔버스가 삭제되면 서버가 그 순간부터 그 사람에게 해당 캔버스 메시지를 보내지 않고 `/user/queue/canvases`로 알린다
  (`{ "type": "revoked" | "deleted", "canvasId": 1 }`). 화면은 구독을 풀고 캔버스 홈으로 간다.
  메모리 브로커는 서버가 구독을 하나씩 끊는 방법을 주지 않아, 서버는 권한 기록에서 빼고 나가는 메시지를 거른다.
- 권한이 보기로 바뀌면 같은 경로로 알리고, 화면은 편집 도구를 숨긴다.

### 5.6 커서 공유와 접속자

- 커서는 **저장하지 않는다**. 이벤트 로그·`seq`·활동 로그에 남기지 않는다. 놓쳐도 다음 위치가 곧 오므로 다시 보내지 않는다.
- 화면은 캔버스 좌표로 보낸다(화면 확대·이동과 무관하게 같은 위치를 가리키도록). 많아야 초당 20번(50ms 간격)만 보낸다. 서버도 사람별로 초당 20번을 넘는 메시지는 버린다.

```json
{ "x": 512.5, "y": 230.0 }
```

- 서버가 보내는 커서 메시지: `{ "user": { "id": 2 }, "x": 512.5, "y": 230.0 }`. 보낸 사람도 받으므로 화면은 `user.id`가 자기면 무시한다.
  (보낸 사람만 빼려면 받는 사람마다 따로 보내야 해서 메시지가 늘어난다. `docs/backend/canvas.md` D18)
- 접속자: 구독하면 `{ "type": "join", "user": {…} }`, 연결이 끊기거나 구독을 풀면 `{ "type": "leave", "user": {…} }`를 보낸다. 지금 접속자 목록은 `/app/canvases/{id}/presence`를 구독하면 한 번 받는다(`{ "users": [{ "id": 1 }] }`).
- 한 사람이 창을 여러 개 열어도 접속자 목록에는 한 번만 나온다.

## 11. 기술 선정: 실시간 전달 방식

> 결정: **편집 저장은 HTTP, 다른 사람의 변경·커서·접속자는 WebSocket(STOMP)**. (2026-11-26, #83)

### 11.1 요구사항

| # | 요구사항 | 근거 |
|---|---|---|
| R1 | 다른 사람이 카드를 옮기거나 프롬프트를 고치면 바로 보인다 | 실시간 동시 편집을 MVP에 포함 |
| R2 | 다른 사람의 커서가 바로 보인다. 사람마다 초당 최대 20번 움직임 | 커서 공유를 MVP에 포함 |
| R3 | 커밋된 변경만 전달하고, 놓친 변경은 `seq`로 알아채 다시 받는다 | 5.2, 5.4 |
| R4 | 권한(소유자·편집·보기)을 연결할 때와 메시지마다 확인하고, 공유가 풀리면 바로 막는다 | 4장 |
| R5 | 기존 인증(JWT)을 쓰고 토큰을 주소에 넣지 않는다 | 3장, 로그 노출 방지 |
| R6 | 배포 환경에서 동작한다: backend 파드 1개, Ingress(nginx, TLS), 경로 `/api` | `infra/k8s` |
| R7 | 지금 스택을 유지한다: Spring MVC(서블릿). WebFlux로 바꾸지 않는다 | `backend/CLAUDE.md` 1번 |

### 11.2 후보

| 후보 | 동작 |
|---|---|
| A. WebSocket + STOMP | 연결 하나로 양방향. STOMP로 구독 주소(목적지)와 메시지 형식을 정한다 |
| A'. WebSocket 직접 | 연결 하나로 양방향. 메시지 형식·구독·라우팅을 직접 만든다 |
| B. SSE (Server-Sent Events) | 서버 → 화면 한 방향 스트림(HTTP 응답을 열어 둠) |
| C. 짧은 폴링 | 화면이 N초마다 `GET /canvases/{id}/events?after={seq}` |
| D. 긴 폴링 | 서버가 새 변경이 생길 때까지 요청을 붙잡았다가 응답 |

### 11.3 비교

| 기준 | A. WebSocket+STOMP | B. SSE | C. 짧은 폴링 | D. 긴 폴링 |
|---|---|---|---|---|
| R1 변경 반영 지연 | 거의 즉시 | 거의 즉시 | 평균 N/2초 (1초 주기면 최대 1초) | 거의 즉시 |
| R2 커서 (화면 → 서버, 초당 20번) | 같은 연결로 보냄 | 한 방향이라 커서마다 HTTP 요청이 따로 필요 (사람마다 초당 20번) | 불가에 가까움 | 불가에 가까움 |
| R3 놓친 변경 | `seq` 확인 후 재조회 (직접 구현) | `Last-Event-ID`로 이어받기 기본 제공 | `after={seq}`로 자연스러움 | `after={seq}`로 자연스러움 |
| R4 권한 회수 | 서버가 구독을 찾아 끊음. 구독·보내기마다 인터셉터로 확인 | 서버가 연결을 찾아 끊음 | 매 요청 확인 (자동) | 매 요청 확인 (자동) |
| R5 인증 | 브라우저 WebSocket은 헤더 불가 → STOMP `CONNECT` 헤더로 토큰 전달 (표준 방식) | 브라우저 `EventSource`는 헤더 불가 → fetch 기반 라이브러리 필요 | 일반 헤더 | 일반 헤더 |
| R6 Ingress(nginx) | 업그레이드 기본 지원. 60초 무응답 끊김 → 10초 하트비트로 해결 (Ingress 설정 변경 없음) | 버퍼링 끔(응답 헤더), 60초 → 핑으로 해결 | 신경 쓸 것 없음 | 타임아웃보다 짧게 대기 |
| R7 Spring MVC | `spring-boot-starter-websocket` (Boot 관리) | `SseEmitter` (기본 포함) | 기본 | 비동기 요청 |
| 구현 양 (서버) | 중간: 설정, 인터셉터, 구독 관리 | 작음~중간 | 가장 작음 | 중간 |
| 구현 양 (화면) | STOMP 라이브러리, 재연결 | 라이브러리, 자동 재연결 | 가장 작음 | 요청 반복 |
| 파드를 여러 개로 늘릴 때 | 파드 간 메시지 공유 필요 (외부 브로커 또는 DB 알림) | 같음 | 필요 없음 (DB만 봄) | 같음 |
| 부하 (사용자 20명) | 연결 20개, 변경·커서 있을 때만 전송 | 연결 20개 + 커서용 HTTP 요청 다수 | 변경이 없어도 초당 20번 DB 조회 (1초 주기) | 연결 20개 |

### 11.4 선정 이유

1. **커서 공유(R2)가 결정적이다.** 커서는 화면에서 서버로 자주 보내는 짧은 메시지다. SSE·폴링은 서버 → 화면 한 방향이라, 커서를 보내려면 움직일 때마다 HTTP 요청을 따로 만들어야 한다. WebSocket은 이미 열린 연결 하나로 보내고 받는다.
2. **편집 저장은 HTTP로 남긴다.** 저장에는 트랜잭션, `requestId` 재전송, 글 충돌(409) 응답이 필요하다. HTTP 요청 하나에 성공·실패가 바로 돌아와야 재전송 규칙(5.2)이 단순하다. WebSocket으로 저장까지 하면 요청-응답 짝 맞추기, 실패 재시도, 순서 보장을 직접 만들어야 한다.
3. **STOMP를 쓴다 (WebSocket 직접이 아니라).**
   - 캔버스별 구독 주소(`/topic/canvases/{id}/…`), 나에게만 오는 알림(`/user/queue/…`)을 Spring이 기본으로 제공한다.
   - 인증을 `CONNECT` 헤더로 넘기는 방식이 정해져 있어 토큰을 주소에 넣지 않아도 된다(R5).
   - 구독·보내기마다 권한을 확인하는 지점(채널 인터셉터)이 있다(R4).
   - 하트비트가 프로토콜에 있어 Ingress 60초 끊김을 설정 변경 없이 피한다(R6).
   - 메시지 형식·라우팅·하트비트를 직접 만들 필요가 없다.
4. **Spring MVC를 그대로 쓴다(R7).** `spring-boot-starter-websocket`은 Spring Boot가 버전을 관리하고 서블릿 스택에서 동작한다.

**고르지 않은 이유**

| 후보 | 이유 |
|---|---|
| B. SSE | 서버 → 화면만 필요했다면 가장 단순했다. 커서 공유가 들어오면서 화면 → 서버 경로를 따로 둬야 해서 탈락 |
| C. 짧은 폴링 | 반영이 최대 N초 늦어 동시 편집 느낌이 나지 않고 커서 공유가 사실상 불가. 변경이 없어도 DB를 계속 조회 |
| D. 긴 폴링 | 지연은 줄지만 구현 복잡도는 SSE와 비슷하고, 커서 공유 문제는 그대로 |
| A'. WebSocket 직접 | 구독·라우팅·인증·하트비트를 직접 만들어야 한다. STOMP가 이미 해결한 것을 다시 만드는 셈 |

### 11.5 결과와 주의할 점

- backend 의존성: `spring-boot-starter-websocket` (Boot BOM 관리, 버전 표기 없음).
- 화면 의존성: STOMP 클라이언트(`@stomp/stompjs` 제안). 버전은 후보와 근거를 보여 주고 확인받아 고정한다(10장).
- 메시지 브로커: 지금은 서버 안 메모리 브로커(simple broker). backend 파드가 1개라 충분하다.
- **파드를 여러 개로 늘리면** 다른 파드에 연결된 사람에게도 메시지가 가야 한다. 이때 PostgreSQL `LISTEN/NOTIFY`(새 인프라 없음) 또는 외부 브로커(RabbitMQ·Redis 등)를 붙인다. 화면 쪽 규약(5.5, 5.6)은 바뀌지 않는다.
- 배포(롤링 업데이트)·재시작 때 연결이 끊긴다. 화면이 다시 연결하고 캔버스를 다시 조회하므로 상태는 잃지 않는다. 커서·접속자는 다시 연결되면 새로 채워진다.
- Ingress 설정(infra)은 바꾸지 않는다. 하트비트(10초)가 nginx 기본 타임아웃(60초)보다 짧기 때문이다. 하트비트를 늘리려면 Ingress 타임아웃도 같이 늘려야 한다.

### 11.6 다시 볼 시점

| 시점 | 확인할 것 |
|---|---|
| backend 파드를 2개 이상으로 늘릴 때 | 메시지 공유 방식(`LISTEN/NOTIFY` vs 외부 브로커) |
| 커서 메시지 때문에 서버 부하가 눈에 띌 때 | 보내기 간격(50ms)을 늘리거나 서버에서 묶어 보내기 |
| 글자 단위 공동 편집을 넣을 때 | 글 버전 충돌(409) 방식 대신 OT·CRDT 같은 병합 방식 검토 |
